# Сервис личного кабинета FuntiDesk

Основание — ADR-009 и проект ADR-010. Это отдельный сервис, который не включает upstream-аккаунты и не меняет семейное доверие. Есть почтовый вход, сессии, подписанная привязка устройств, копии семьи для показа и устойчивые события удаления. Готовность первого этапа подтверждается только реальными клиентами и доставкой писем; эти проверки ещё не выполнены.

## Запуск

Нужны Rust 1.90, отдельный persistent-каталог SQLite, секрет HMAC и собственный отправляющий SMTP. Пример ниже предназначен для отдельной тестовой среды; рабочий сервер им не изменяется.

Для локального запуска нужны также независимый сервис и два разных ключа. Обычный запуск не создаёт пустую базу автоматически. Пример тестового окружения:

```sh
umask 077
mkdir -p /tmp/funtidesk-account-test
openssl rand -hex 32 > /tmp/funtidesk-account-test/account.key
openssl rand -hex 32 > /tmp/funtidesk-account-test/witness.key
export FUNTI_ACCOUNT_KEY_FILE=/tmp/funtidesk-account-test/account.key
export FUNTI_ACCOUNT_DATABASE=/tmp/funtidesk-account-test/account.sqlite3
export FUNTI_ACCOUNT_WITNESS_KEY_FILE=/tmp/funtidesk-account-test/witness.key
export FUNTI_ACCOUNT_WITNESS_NAMESPACE=$(openssl rand -hex 32)
export FUNTI_WITNESS_DIRECTORY=/tmp/funtidesk-account-test/witness
export FUNTI_ACCOUNT_WITNESS_URL=http://127.0.0.1:21802/v1/witness
export FUNTI_ACCOUNT_SMTP_HOST=127.0.0.1
export FUNTI_ACCOUNT_SMTP_PORT=2525
cargo build --manifest-path account/Cargo.toml --locked
account/target/debug/funtidesk-account witness-init
account/target/debug/funtidesk-account witness &
account/target/debug/funtidesk-account initialize
account/target/debug/funtidesk-account
```

После запуска witness нужно дождаться слушающего порта перед `initialize`. Подробный порядок, границы свежести и восстановление только последнего состояния — [ACCOUNT_RECOVERY.md](../docs/ACCOUNT_RECOVERY.md), проект архитектуры — [ADR-011](../docs/ADR-011-account-recovery.md). В production независимое состояние размещается на другой машине; локальный пример этого не доказывает.

При обычном перезапуске сервиса действующие сессии и лимиты сохраняются, незавершённые challenge/nonce отменяются. Отзывы email-сессий включены в независимое подтверждение.

Секрет создаётся вне репозитория и хранится с правами `0600`. Нет встроенного секретного значения, SMTP-пароля, внешней отправки почты или запасного API. Без корректного файла ключа сервис не запускается. По умолчанию слушает `127.0.0.1:21800`; наружу API выдаётся только через HTTPS Caddy.

`FUNTI_ACCOUNT_TRUSTED_PROXIES` — список точных IP Caddy. Caddy должен **перезаписывать** заголовок `X-Funti-Client-IP` реальным адресом подключившегося клиента; forwarded-заголовки от произвольного peer игнорируются. Требуется Host `desk.funti.cc` либо `desk.funti.cc:443`. Браузер и API используют один origin.

`FUNTI_ACCOUNT_REGISTRY_SOCKET` — отдельный Unix socket hbbs, по умолчанию `/run/funtidesk-identity/hbbs.sock`. В hbbs включается только явным `FUNTI_ACCOUNT_IDENTITY_SOCKET`; при отсутствии этой переменной прежний запуск не меняется. `FUNTI_ACCOUNT_IDENTITY_GID` определяет группу доступа к socket, по умолчанию `10001`. Каталог socket должен иметь группу account и разрешать ей проход; каталог ключей hbbs сервису аккаунтов не передаётся. Ошибка resolver закрывает привязку устройства, а hbbs продолжает работать.

## API

Все пути ниже находятся под `/api/account/v1`. `/health` не содержит данных аккаунта. Управляющие запросы — POST. Лимит тела — 64 КиБ, одновременно обрабатывается не более 32 API-запросов, срок обработки ограничен 20 секундами. Ошибки базы и SMTP не раскрывают почту, код или токен.

| Путь | Назначение |
|---|---|
| GET `/auth/bootstrap` | Контекст входа и CSRF для браузера; нативному клиенту — секрет контекста |
| POST `/auth/request` | `{email}` → challenge на 5 минут; код уходит только через собственный SMTP |
| POST `/auth/verify` | `{challenge_id,code}` → одна сессия; максимум 5 попыток |
| GET `/session` | Собственный аккаунт, срок и браузерный CSRF |
| POST `/logout`, `/logout-all` | Немедленный отзыв на сервере |
| GET `/devices`, `/family` | Устройства и копии семьи без прав |
| POST `/devices/bind/nonce`, `/devices/bind` | Одноразовый вызов и подпись существующим ключом устройства с проверкой реестра hbbs |
| POST `/devices/{id}/family/nonce`, `/devices/{id}/family` | Подписанная копия только собственной службы |
| POST `/family/remove` | `{target_pk,request_id}` → устойчивое удаление; повтор request_id идемпотентен |
| GET `/family/removals` | Ожидание доставки и подтверждения служб |
| POST `/devices/{id}/sync/nonce`, `/devices/{id}/sync` | Подписанный ограниченный канал своих событий, независимо от почтовой сессии |
| POST `/devices/{id}/ack/nonce`, `/devices/{id}/ack` | Подписанное подтверждение событий только своего источника |

Браузер получает `__Host-` cookie с `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/`, без `Domain`. Изменение требует точный Origin и `X-Funti-CSRF`. Токен не выдаётся браузеру в JSON и не хранится в веб-хранилище.

Нативный клиент явно передаёт `X-Funti-Client: native`, до входа — `X-Funti-Login`, после — Bearer. Cookie в этом режиме запрещены. Чужой Origin отклоняется в обоих режимах. Отсутствие браузерного Origin не превращает cookie в нативную авторизацию.

Для вызовов устройства поле `payload_hash` — SHA-256 JSON payload после сортировки ключей объектов; массивы сохраняют порядок, сериализация компактная UTF-8. Выданный nonce содержит поля сообщения; подпись проверяется по точным байтам `Nonce::message()`. Служба клиента должна самостоятельно проверить назначение и собрать эти байты, а не подписывать произвольное сообщение сервера. Nonce живёт 5 минут и расходуется атомарно.

Ключ глобально закреплён за одной идентичностью; повтор bind в своём аккаунте сохраняет её и обновляет адрес FuntiDesk и метаданные, переход в чужой аккаунт отклоняется. Новый ключ при прежнем ID создаёт новую идентичность без копии семьи и прав. Одновременно выданные source nonce независимы: новый запрос не отменяет уже подписываемый запрос службы.

Копия загружается как `{name,version,members:[{id,name,pk}]}`. Поле `rights` и другие неизвестные поля не принимаются. Максимум 64 устройства аккаунта и 128 членов одной копии. Копии не преобразуются в локальное доверие.

Выдача nonce ограничена 240 разрешёнными запросами в минуту с одного IP и 600 глобально. Это покрывает минутный sync/ack/family обмен 64 источников за одним NAT; отказ по локальному лимиту не расходует общий бюджет.

Sync подписывает `{after:<локальный устойчивый курсор>}`, ack — `{events:[<номера>]}`. События хранятся независимо от подтверждений: восстановленный клиент с меньшим курсором может получить уже подтверждённое удаление. Новое привязанное устройство получает предыдущие удаления аккаунта. Служба применяет удаление и сохраняет отметку **до** продвижения курсора и ack. Серверный ack сам по себе не доказывает, что старая клиентская версия умеет менять локальную семью.

Список `/family/removals` ограничен 4096 строками доставки. При `has_more: true` интерфейс обязан сообщить о неполном списке и не делать вывод о завершении всех удалений только по показанным строкам.

## Проверки и границы поставки

```sh
cargo fmt --manifest-path account/Cargo.toml -- --check
cargo clippy --manifest-path account/Cargo.toml --all-targets --locked -- -D warnings
cargo test --manifest-path account/Cargo.toml --locked
```

Проверяются настоящие маршруты API, Ed25519-подписи, одноразовость при гонках, Origin/CSRF, границы аккаунтов, смена ключа, выход из всех сессий, повторная доставка удалений и сохранение лимитов после перезапуска SQLite. Отдельные проверки используют локальный Unix socket. Письма тестовых запросов остаются в памяти; внешние почтовые ящики этими тестами не используются.

До рабочего запуска нужны: завершённая интеграция службы и интерфейсов клиента, защищённое хранение его токена; воспроизводимые SMTP/DKIM и закрытая сеть; согласованный патч Caddy и DNS; утверждённая схема независимого состояния ADR-011 и проверка восстановления на отдельной машине; утверждённые сроки хранения и удаление аккаунта; реальные Windows-клиенты, браузер и доставка во входящие Gmail/Яндекса/Mail.ru. Эти свойства нельзя вывести из успешных API-тестов.
