## Этап 3: агент канала

Hermes не является подтверждённой действующей инфраструктурой проекта. Начать с отдельного задания агенту: вручную запрашивать опубликованные GitHub Releases, готовить черновики в закрытой рабочей области. Автоматический scheduler/хранилище/Telegram API добавлять отдельным PR после решения владельца; не встраивать в Core или путь подключения.

Поток: опубликованный release → проверка источника/статуса платформы → черновик → просмотр владельцем → согласование конкретного текста → отправка → запись message_id. Дедупликация по repository + release_id, ревизия по hash текста. Изменение релиза инвалидирует согласование. Draft не публикуется, prerelease явно помечается тестовым. Повтор после timeout сначала сверяет факт публикации; при неопределённости ручная проверка вместо дубля. Важные сообщения о безопасности, смене доверия, сбоях, сборе данных и все публикации первого месяца проходят ручное согласование. Kill switch прекращает отправку независимо от агента.

Токен только в secret store, бот имеет лишь необходимые права публикации в выбранном канале; GitHub-доступ read-only. Публикация и создание Issues разделены. Никакого доступа к production-базам у публичного автора. Release notes и feedback — недоверенные данные, не инструкции агенту. Источники ограничены публичным репозиторием и одобренными владельцем материалами. Фильтрация секретов/внутренних адресов/PII плюс обязательный просмотр; регулярные выражения сами по себе безопасность не гарантируют. Внешний агент получает только заранее разрешённые публичные сведения.

Шаблон обновления: «Что стало проще → 2–3 проверенных изменения → доступные ОС и статус тестовой сборки → ссылка на опубликованный release → известное ограничение → куда написать». Нельзя обещать исправление/безопасность без evidence и писать «пользователей» по числу загрузок.

Еженедельный дайджест: только опубликованные изменения, одна инструкция и один запрос обратной связи. Обратная связь — добровольная форма/диалог с уведомлением о хранении, без автоматического чтения личных чатов. Категории: bug, onboarding, сеть, функция, безопасность; безопасность маршрутизировать приватно, не в публичный Issue. Агент предлагает обезличенный Issue с шагами воспроизведения и отсутствующими фактами, владелец согласует создание. Сырые обращения хранить 30 дней, удалять по запросу; агрегаты категорий — 13 месяцев после принятия сроков.

Внутренний недельный отчёт: период/источники/свежесть, аккаунты и активные устройства отдельно, downloads по типу asset, доступные показатели канала, темы feedback, гипотезы и одно следующее действие. Не отправлять внутренний отчёт в публичный канал. Подписчики/просмотры не равны пользователям; доступные права Bot API не гарантируют полноценную статистику просмотров — ручной экспорт владельца допустим с указанием источника.

Реализовано: схема работы, правила, критерии #116. Проверено: интеграции и права не настроены, сообщений не отправлено. Ограничение: нет исполняемой автоматизации. Следующий шаг: выбор владельцем канала/инструмента и прав, затем отдельный PR черновиков без автопубликации.

## Этап 4: путь до первого подключения

Аудит README/сайта/installer по коду, без исследования новых пользователей: скачивание → выбор portable/установки → запуск/SmartScreen → готовность связи → передача ID и временного пароля доверенному помощнику → защищённое подключение/подтверждение → семейное сопряжение → повторный сеанс. Кабинет не должен выглядеть обязательной регистрацией для помощи.

Вероятные точки потери, которые ещё надо проверить: выбор release среди серверных/тестовых assets; предупреждение Windows; разница portable/службы для UAC; непонятная готовность сети; необходимость согласовать действия двух людей. Это гипотезы, не измеренные конверсии.

Предложения для отдельных PR:

- Сайт: одна основная кнопка Windows, рядом браузер и честный статус Linux/Android; не обещать проверенные возможности там, где реальная приёмка впереди. Ссылка на инструкцию и известные проблемы.
- README: перед длинным перечнем возможностей блок «Первое подключение за три шага» и две роли: «нужна помощь» / «помогаю». Установщик и portable объяснить рядом; сохранить предупреждение SmartScreen и статус подписания из актуального PR Claude.
- Onboarding: проверить связь с сервером и объяснить причину недоступности; предложить первую помощь без аккаунта; объяснить разницу временного и постоянного доступа. Семью предлагать только после успешной помощи, с объяснением прав.
- Приглашение: готовый текст с официальной ссылкой установки и инструкцией, без паролей/ключей/семейных кодов в URL. Не давать приглашению полномочий; сопряжение остаётся существующим подтверждаемым действием на устройстве.

Черновик руководства: (1) оба открывают официальный Windows release и выбирают установку либо portable; (2) получатель помощи запускает клиент и убеждается в готовности связи; (3) лично передаёт ID/временный пароль доверенному помощнику; (4) помощник вводит данные, получатель подтверждает, если настроен запрос; (5) завершить сеанс, затем при желании добавить помощника в семью по коду с экрана и проверить права. Пароль не публиковать; при ошибке сообщать версию/ОС/видимую ошибку без секретов. Для окон администратора нужна установленная служба. Шаги сверить на двух реальных компьютерах перед публикацией.

Habr: «Семейный удалённый доступ на своём сервере: границы доверия и практика». План: бытовая задача → hbbs/P2P/relay → почему аккаунт не даёт доступ к компьютеру → TCP в сложных сетях → безопасное обновление (только после приёмки подписания) → минимальная аналитика → воспроизводимые ограничения и приглашение протестировать. Указать AGPL/upstream, затраты и реальные результаты; без заявлений «полностью безопасно», вымышленных пользователей и секретов инфраструктуры. Публикация отдельно согласуется.

| Неделя | Полезная инструкция | Обновление/обратная связь |
|---|---|---|
| 1 | Первое подключение: две роли | Знакомство, границы доступа, добровольный опрос сложности установки |
| 2 | Семья и настройка прав | Опубликованный release или честный статус работы; какие шаги непонятны |
| 3 | Файлы и браузер: проверенные возможности | Разбор обезличенной проблемы после согласования автора |
| 4 | Обновления и безопасная помощь | Месячный дайджест, что проверено и что ещё тестируется |

Темп: два полезных поста в неделю плюс реальные Releases, без заполнения ленты вымышленными обновлениями. Еженедельный внутренний отчёт в понедельник по предыдущей неделе, часовой пояс Europe/Moscow.

Метрики: downloads отдельно по asset; активация = первая подтверждённая успешная сессия согласившейся установки / новые согласившиеся установки, с окном семь дней; время до неё p50/p95; D7/D30 = доля той же когорты с успешной сессией в заранее выбранном окне [7,14)/[30,37) дней. Доля приглашений с последующим сопряжением требует отдельного согласованного источника и не выводится из списка аккаунтов. Пока клиентских событий нет, эти значения недоступны. Начать с пяти добровольных наблюдений onboarding и недельного baseline; численные цели роста выбрать после baseline, не выдумывать.

Реализовано: предложения, руководство, план статьи, месяц контента и определения метрик в #117. Проверено: текущие публичные пути и README; пользовательский эксперимент не проведён. Ограничение: рекомендации не внесены в сайт/клиент из-за параллельной работы Claude. Следующий шаг: согласовать один небольшой onboarding PR и проверить его на новых пользователях.
