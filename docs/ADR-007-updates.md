# ADR-007: Обновление кнопкой и удалённое обновление

**Статус:** принято владельцем 2026-10-11 (модель доверия к обновлениям). Реализация: этап 1 — кнопка для копии, установленной `install.ps1` (2026-10-11); установленный режим (служба) и удалённое обновление — следующие этапы.
**Дата:** 2026-10-11.
**Связано:** `docs/ROADMAP.md` (M4, «Обновление кнопкой»), `install.ps1`, `docs/SECURITY.md`, нумерация сборок `1.4.9-ft.N` (`client/build.rs`, `FUNTI_BUILD`).

## Проблема

Обновить FuntiDesk сейчас можно только командой `install.ps1`. Владелец хочет кнопку «Обновить» в клиенте и обновление компьютера члена семьи из сеанса, без подтверждения на той стороне (решение 2026-10-09).

Обновление ставит скачанную программу с правами FuntiDesk, а в установленном режиме — с правами службы. Поэтому нужно решить, чему клиент доверяет при скачивании.

## Чего опасаемся

Если чужая программа уже запущена на компьютере, обновление ничего не меняет: компьютер и так скомпрометирован. Здесь риск в другом. Все компьютеры семьи сами берут обновления из одного места — релизов `michailr1/FuntiDesk` на GitHub — и ставят их без вопросов. Подмена файла в этом месте разносится по всем компьютерам автоматически.

Пути подмены по убыванию вероятности:

1. **Захват аккаунта GitHub владельца** (пароль, токен, сессия) — злоумышленник публикует свой релиз.
2. Взлом сборки в CI (зависимость, action) — маловероятно, actions закреплены по хешу коммита.
3. Подмена по дороге — HTTPS к `github.com` её практически исключает.

Подпись релизов защищает от пути 1, только если ключ подписи хранится **вне GitHub**. Ключ в секретах GitHub Actions от захвата аккаунта не помогает: захвативший запустит CI, и тот подпишет его файл.

## Решение владельца (2026-10-11)

**Пока без подписи релизов.** Доверие к обновлению то же, что у `install.ps1`:

- источник — только `https://github.com/michailr1/FuntiDesk/releases/latest/download/…`, адрес зашит в клиент, никаких зеркал и запасных адресов;
- только HTTPS с проверкой сертификата;
- проверка SHA256 по `SHA256SUMS.txt` того же релиза (защищает от битой загрузки, не от подмены);
- аккаунт GitHub владельца защищён двухфакторным входом.

**Принятый риск:** захват аккаунта GitHub владельца означает подмену обновления на всех компьютерах семьи, которые обновятся после этого.

**Путь усиления (когда понадобится):** подпись релизов ключом, который хранится только у владельца (не в GitHub), и открытый ключ, зашитый в клиент. Клиент ставит только подписанное, при несовпадении — отказ (fail closed). Формат релиза ниже оставляет для этого место.

## Как работает обновление

### Версия релиза

- В каждый Windows-релиз CI кладёт `funtidesk-version.txt` с версией `1.4.9-ft.N` и вносит его в `SHA256SUMS.txt`.
- Клиент сравнивает только `N` (`FUNTI_BUILD`). Обновление предлагается, если `N` релиза больше своего. Сборка с `N = 0` (номер неизвестен, например локальная из shallow-клона) обновление не предлагает сама, только по явной кнопке.
- Откат на меньший `N` клиент не делает.

### «Обновить» на своём компьютере

1. «О программе»: «Проверить обновления» → «Доступна версия 1.4.9-ft.N» → «Обновить».
2. Клиент скачивает `funtidesk-version.txt`, `SHA256SUMS.txt`, `FuntiDesk-windows-x64.zip`, сверяет SHA256. Любая ошибка — сообщение и отказ, установленная версия не трогается.
3. Замена файлов и перезапуск с тем же профилем — та же последовательность, что в `install.ps1` (остановить процессы FuntiDesk, распаковать, запустить). В установленном режиме замену выполняет служба.

### Удалённое обновление из сеанса

1. При подключении клиент получает версию той стороны (своё поле протокола, номер от 1000; старая сторона его не присылает — считается «неизвестна, обновление не предлагается»).
2. Если она старше последнего релиза — в окне сеанса «На той стороне старая версия FuntiDesk» и кнопка «Обновить».
3. Кнопка доступна только в сеансе управления (у помощника и так есть полный доступ к компьютеру). Помощник передаёт только команду «обновись»; **что и откуда скачать, решает сама та сторона** по правилам выше. Адрес, файл или хеш от помощника не принимаются.
4. На той стороне — без подтверждения (решение владельца 2026-10-09), но видимое окно без кнопок «FuntiDesk обновляется, сейчас переподключимся». Скрытых действий нет.
5. Сеанс переподключается к обновлённой стороне.

## Последствия

- Обновление не добавляет нового входящего канала: команда идёт только внутри уже авторизованного сеанса управления.
- Проверка «есть ли новая версия» — один HTTPS-запрос к GitHub; без интернета или при ошибке ничего не происходит.
- Android обновляется отдельно (магазин или APK), этот ADR — только Windows.

## Реализация, этап 1 (2026-10-11)

Код — `client/src/funti_update.rs`, кнопка — «О программе» (`desktop_setting_page.dart`, `_FuntiUpdate`), CI — `ui-windows-artifact.yml` (`funtidesk-version.txt`).

- Обновляется только копия в `%LOCALAPPDATA%\Programs\FuntiDesk` (туда ставит `install.ps1`). Служба (установленный режим) и другие копии (папка сборки, `FuntiDesk-portable.exe`) получают объяснение и кнопку не видят — fail closed до следующего этапа.
- Загрузка: адрес релиза зашит; только HTTPS (rustls, проверка сертификата), без прокси; перенаправления — только на `github.com` и `*.githubusercontent.com`. `funtidesk-version.txt` и архив сверяются с `SHA256SUMS.txt`; `N` релиза должен быть больше своего (или свой `0`).
- Замена: архив распаковывается в `Programs\FuntiDesk.update\files` (пути внутри архива проверяются), оттуда запускается **новый** `FuntiDesk.exe --funti-finish-update <pid> <папка>`, старый закрывает свои процессы и выходит. Новый проверяет, что папка — именно `Programs\FuntiDesk`, а сам он запущен из `FuntiDesk.update\files`, ждёт выхода старого, переименовывает папку в `FuntiDesk.old`, копирует новые файлы, запускает установленный FuntiDesk. Ошибка копирования — папка возвращается из `.old`, запускается прежняя версия. Остатки (`.old`, `.update`) удаляются при следующем обычном запуске. Профиль (`%APPDATA%`) не трогается.
- Аргумент `--funti-finish-update <pid> <папка>` вызывает старая версия у новой, поэтому все следующие версии обязаны его принимать.
