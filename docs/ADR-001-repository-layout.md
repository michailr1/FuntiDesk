# ADR-001: структура репозитория и импорт upstream

Статус: принято

Дата: 2026-09-17

## Контекст

Baseline FuntiDesk состоит не из двух, а из трёх upstream-репозиториев:

- клиент `rustdesk/rustdesk` 1.4.9;
- сервер `rustdesk/rustdesk-server` 1.1.16;
- общий репозиторий `rustdesk/hbb_common`, подключённый к клиенту и серверу на разных commit pin.

На baseline-версиях:

- клиент использует `hbb_common` commit `7e1c392c62d39c364127307cd408421dd5f8cfb0`;
- сервер использует `hbb_common` commit `83419b6549636ee39dacef7776c473f5802e08d6`.

Сводить эти версии к одному commit до воспроизводимой baseline-сборки означало бы менять ядро сразу двух компонентов без продуктовой необходимости.

## Решение

Используем монорепозиторий FuntiDesk со следующей структурой:

```text
/client
/client/libs/hbb_common
/server
/server/libs/hbb_common
/docs
/infra
```

`hbb_common` импортируется дважды, каждая копия сохраняет свой upstream pin.

Импорт должен быть history-preserving. Предпочтительный механизм — `git subtree` либо эквивалентный импорт с сохранением upstream history.

При импорте клиента и сервера их gitlink `libs/hbb_common` не считается конечным содержимым: после импорта основного дерева в соответствующий путь импортируется конкретная зафиксированная версия `hbb_common`.

## Почему не единая копия hbb_common

Единая копия потребовала бы выбрать одну из двух версий или самостоятельно объединить их. Это создаёт изменение совместимости до получения эталонной сборки и усложняет диагностику.

## Почему не submodule

Production-сборка FuntiDesk должна быть воспроизводима из нашего репозитория и наших зафиксированных источников. Критическая часть исходников не должна зависеть от доступности внешнего Git-репозитория во время сборки.

## Почему не отдельные репозитории

Для небольшой команды единый продуктовый репозиторий упрощает синхронизацию client/server pin, документацию, CI и релизы.

## Политика повторного импорта hbb_common

1. Клиентская и серверная копии обновляются независимо.
2. Новый pin принимается только вместе с соответствующим upstream client/server release либо обоснованным security backport.
3. Запрещено автоматически синхронизировать обе копии на один commit ради унификации структуры.
4. Любое обновление одной из копий фиксируется в `docs/UPSTREAM.md` и проходит релевантную baseline/E2E-проверку.
5. Наши изменения в `hbb_common` должны быть минимальными и помечаться как FuntiDesk-specific там, где это помогает при последующем merge.

## Последствия

В репозитории будет дублирование части исходников, но оно отражает реальную зависимость baseline и уменьшает риск неявной несовместимости.
