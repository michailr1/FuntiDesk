# ADR-004: Сигнальный канал по TCP и собственная сборка сервера

**Статус:** предложено, ждёт решения владельца.
**Дата:** 2026-10-08.
**Связано:** MIK-16 (NAT refresh), `docs/reviews/2026-10-08-pr12-windows-acceptance.md`, `docs/SERVER_DEPLOYMENT.md`, `docs/SECURITY.md`.

## Проблема

Подключение к компьютеру за некоторыми роутерами или провайдерами не проходит, хотя компьютер показывает «В сети». Подтверждено 2026-10-08 на ноутбуке владельца (`440171008`, домашний роутер `192.168.1.51`, внешний адрес `109.173.98.95`):

- клиент регистрируется на `hbbs` по UDP 21116 раз в 15 секунд, ответы (2 байта) доходят;
- запрос на подключение `hbbs` отправляет тем же UDP на тот же адрес и порт (`PunchHole`, 38 байт, три попытки) — `tcpdump` на сервере видит отправку, `pktmon` на ноутбуке видит, что ни один такой пакет до Wi-Fi-адаптера не дошёл;
- запрос, отправленный через 1,7 секунды после регистрации, тоже теряется, значит, частая регистрация не поможет;
- входящий UDP режет сеть до ноутбука (роутер или провайдер), а не Windows, брандмауэр или FuntiDesk.

Такие сети встретятся и у семьи, поэтому это блокер продукта, а не частный случай.

## Варианты

1. **Чаще регистрироваться по UDP.** Не решает: пакет отбрасывается и через 1,7 секунды после регистрации.
2. **Настраивать роутеры.** Не масштабируется на семью и друзей.
3. **Сигнальный канал по TCP.** Клиент держит постоянное исходящее TCP-соединение с `hbbs` и получает по нему запросы на подключение. Исходящий TCP пропускают практически все сети.

## Решение

Вариант 3.

**Клиент.** Режим уже есть в ядре upstream (`RendezvousMediator::start_tcp`, включается опцией `disable-udp`): соединение с `desk.funti.cc:21116`, обмен ключами `secure_tcp` со встроенным ключом сервера, регистрация ключа `RegisterPk`, приём `PunchHole`/`RequestRelay`/`FetchLocalAddr` и ответы по тому же соединению, пустые кадры как heartbeat, переподключение при тишине дольше `keep_alive × 1,5`. В FuntiDesk включить его по умолчанию через `DEFAULT_SETTINGS` (`disable-udp = Y`). Прямые соединения сохраняются: TCP hole punching работал в проверке 2026-10-08. Закреплённые сервер и ключ (R-12) не меняются.

**Сервер.** OSS `hbbs` этот режим не поддерживает: по TCP он принимает только `PunchHoleRequest`/`RequestRelay`/`RelayResponse`, `RegisterPk` по TCP отвечает `NOT_SUPPORT`, а запросы принимающей стороне шлёт только по UDP. Нужна собственная сборка `hbbs` из `/server` (сейчас production использует upstream image, `/server` не участвует), доработки:

- принимать `RegisterPk` по TCP с теми же проверками, что и по UDP (uuid, pk, IP blocker, частота), отвечать `RegisterPkResponse` с `keep_alive`, не закрывать соединение;
- хранить соответствие «ID устройства → TCP-соединение», удалять его при разрыве;
- отправлять пустой heartbeat чаще, чем истекает 30-секундный тайм-аут чтения (например, раз в 15 секунд), обновлять `last_reg_time` по ответам, чтобы статус «в сети» и `OnlineRequest` работали;
- адресовать `PunchHole`, `RequestRelay` и `FetchLocalAddr` в TCP-соединение устройства, если оно есть, иначе по UDP, как сейчас (совместимость с устройствами в UDP-режиме);
- обмен ключами `KeyExchange` при открытии TCP-соединения: клиент ждёт его 18 секунд (`READ_TIMEOUT`). В импортированном `/server` его нет — проверить на развёрнутом image и при необходимости реализовать с тем же ключом сервера.

**Сборка и развёртывание сервера.** По правилу `docs/SERVER_DEPLOYMENT.md`: воспроизводимая сборка image в CI, фиксация digest, rollback на текущий upstream image (`sha256:5c5d42fe…`), повторная приёмка M1 и проверка M3. На том же хосте работает VPN-стек владельца (`remnawave`, `caddy`), его не трогать.

## Последствия

- Плюсы: устройства доступны за роутерами, режущими входящий UDP; меньше зависимости от NAT; продукт не требует настройки сети.
- Минусы: поддерживаем свой форк сервера (патч поверх upstream, синхронизация при обновлениях); постоянное TCP-соединение на каждое устройство — для семьи нагрузка ничтожна.
- Безопасность: новый код на сервере обрабатывает данные до аутентификации устройства — те же лимиты и проверки, что у UDP-регистрации; без новых портов; fail closed при ошибке (клиент переподключается к тому же закреплённому серверу, без fallback).
- Совместимость: старые клиенты в UDP-режиме продолжают работать.

## Проверка

1. Ноутбук `440171008` на той же сети: подключение с другого компьютера, P2P и relay, камера.
2. Регрессия: компьютер за VPN, перезапуск сервера (клиенты переподключаются), разрыв сети на клиенте, статус «в сети».
3. Нагрузка: десятки устройств, утечки соединений при обрывах.
4. Rollback на upstream image проходит и клиенты возвращаются к работе. В TCP-режиме против upstream-сервера они регистрироваться не смогут, поэтому клиентский переключатель выпускать только после развёртывания сервера.
