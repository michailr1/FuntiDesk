# ADR-018: подпись релизов ключом владельца

Статус: решение владельца 2026-11-09 «подпись обновлений делаем, это безопасность». Этап 1 (проверка в клиенте и установщике, выключена до появления ключа) — PR из ветки `claude/release-signing`. Этап 2 (ключ владельца, включение) **отложен решением владельца 2026-11-11**: «пока оставим без ключа, на GitHub стоит двухфакторка». Релизы выходят по прежнему порядку, ведущий разработчик выпускает их сам. Владелец создал ключ и передал публичную часть; она сохранена ниже, в разделе «Отложенное включение», в списки не добавлена. Обсуждался вариант второго ключа на сервере DE для подписи агентом — не принят, тоже там.

## Проблема

Клиент и `install.ps1` сверяют SHA-256 файлов с `SHA256SUMS.txt` из того же релиза (ADR-007). Это защищает от повреждения при загрузке, но не от подмены: кто может опубликовать релиз на GitHub, тот меняет и файл, и его контрольную сумму. Репозиторий публичный, сборка публикует релиз сама, а установленная служба ставит обновление с правами SYSTEM. Украденный токен GitHub, чужая сессия агента или ошибка в workflow дают выполнение кода на всех семейных компьютерах.

## Решение

Релиз принимается только с подписью владельца, сделанной ключом, которого нет на GitHub.

- **Что подписывается.** Файл `SHA256SUMS.txt`: в нём суммы архива, portable-файла, версии и «что нового». Номер сборки уже в нём, и клиент ставит только больший номер (ADR-007), поэтому старый подписанный релиз подсунуть нельзя.
- **Чем.** Ключ Ed25519 владельца и `ssh-keygen -Y sign -n funtidesk-release SHA256SUMS.txt`. OpenSSH встроен в Windows 10 и 11, новых программ не нужно. Результат — `SHA256SUMS.txt.sig`, владелец прикладывает его к релизу.
- **Где ключ.** Приватный — только на компьютере владельца, с паролем; копия — на отдельном носителе. Его нет в репозитории, в секретах GitHub, на сервере и у агентов. Публичный — в трёх местах, которые должны совпадать: `RELEASE_KEYS` в `client/src/funti_release_sig.rs`, `$releaseKeys` в `install.ps1`, `infra/release/allowed_signers`.
- **Проверка в клиенте.** `funti_release_sig.rs` разбирает подпись OpenSSH (PROTOCOL.sshsig) и принимает только Ed25519 поверх SHA-512, только назначение `funtidesk-release`, только ключ из встроенного списка. Все три пути обновления (кнопка, служба, обновление из сеанса) и «что нового» берут `SHA256SUMS.txt` через одну функцию. Нет подписи или она не подходит — обновления нет (fail closed), сообщение об ошибке.
- **Проверка в установщике.** `install.ps1` проверяет ту же подпись через `ssh-keygen -Y verify`. Нет OpenSSH или подпись не подходит — установка отменяется.
- **Публикация.** Сборка выкладывает релиз как prerelease: `releases/latest`, откуда берут клиент и установщик, на него не указывает. Владелец подписывает и прикладывает подпись, затем запускает workflow `Release promote`: тот проверяет подпись и суммы всех файлов и только тогда делает релиз «последним». У workflow нет ключа, он ничего не подписывает.

## Чего это не закрывает

- **Исходный код.** Подпись подтверждает, что владелец одобрил именно эти файлы, но собирает их по-прежнему GitHub Actions из `main`. Вредный коммит в `main` попадёт в сборку, и владелец подпишет её, если не заметит. Поэтому вместе с подписью нужны защита ветки `main` (только через PR, обязательные проверки) и подтверждение окружения `release` в настройках GitHub — это делает владелец, у агентов таких прав нет.
- **`install.ps1` по ссылке.** Команда `irm … | iex` выполняет сам скрипт без проверки: кто изменит его в `main`, уберёт и проверку подписи. Защита та же — защита ветки. Проверяемый путь первой установки — скачать `FuntiDesk-portable.exe` и сверить его с подписанным `SHA256SUMS.txt`.
- **Уже установленные версии.** Клиенты до включения проверки обновляются по старому правилу. Первый релиз с проверкой они примут без подписи; все следующие — только с ней.
- **Потеря ключа.** Без ключа новый релиз подписать нельзя. Поэтому в списке может быть два ключа: основной и запасной, который хранится отдельно. Смена ключа — релиз, подписанный старым ключом, в котором список уже содержит новый.

## Этапы

1. **Сейчас.** Модуль проверки с тестами на настоящей подписи OpenSSH, проверка в `install.ps1`, workflow `Release promote`, пустые списки ключей. При пустом списке всё работает как раньше: это переходное состояние, а не запасной путь.
2. **После создания ключа владельцем.** Публичный ключ во все три списка; сборка публикует prerelease; порядок выпуска в `docs/RELEASES.md` становится обязательным. С этого релиза проверка включена.
3. **Отдельно.** Подпись Linux-пакета тем же способом; Android подписывается своим ключом приложения.

## Отвергнутые варианты

- **Подпись в CI ключом из секретов GitHub.** Ключ оказался бы там же, где и угроза.
- **Authenticode (сертификат подписи кода).** Платный, для частного лица получить трудно; защищает от предупреждений Windows, но привязку «только наш ключ» всё равно пришлось бы делать отдельно.
- **minisign, GPG.** Нужна отдельная программа у владельца и в `install.ps1`; `ssh-keygen` уже есть в Windows.

## Отложенное включение (2026-11-11)

Риск остаётся прежним: кто получит доступ к GitHub-аккаунту, сможет выпустить обновление для всех клиентов. Сейчас его закрывает только двухфакторная защита аккаунта.

Чтобы включить подпись позже:

1. Публичный ключ владельца от 2026-11-11: `ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIHHZN0RyW9HzZx1xFg1YHhgMoVH40wcxsT5LoOp2o3wq funtidesk-release`. Добавить в `RELEASE_KEYS` клиента и `infra/release/allowed_signers`; сборку `UI Windows artifact` перевести с `--latest` на `--prerelease`. Готовое изменение — коммит `a49bcf4b1` в ветке `claude/release-signing` (отменён следующим коммитом).
2. Первый подписанный релиз; затем ключ в `install.ps1` отдельным PR (скрипт берётся из `main`).
3. Инструкция владельца — `docs/RELEASE_SIGNING.md`.

Вариант «ключ на DE»: отдельный второй ключ на сервере DE, подписывает агент с доступом к DE, GitHub доступа к DE не имеет; ключ владельца остаётся главным и может отозвать ключ DE. Слабее подписи на компьютере владельца (сервер в интернете), но снимает ручной шаг. Потребует записи исключения для DE в `AGENTS.md`.
