# ADR-019: минимальная аналитика FuntiDesk

Статус: **принят проектом 2026-11-10** после ревью архитектора (#118). Номер окончательный (ADR-018 — подпись релизов). Задание: #114. Разрешены: закрытая страница на `desk.funti.cc` за паролем и ежедневный systemd-таймер отчёта по `docs/ACCOUNT_DEPLOYMENT.md`, раздел «Статистика» (#115, #119). Клиентские события (необязательная телеметрия) по-прежнему требуют отдельного решения.

## Решение и простой первый шаг

Начать с ручного чтения согласованных копий существующих SQLite, без изменения Core, hbbs/hbbr, клиента, протокола и схем. `scripts/analytics/snapshot.py` работает локально, без сети, зависимостей и фонового процесса. Ограничения: 64 MiB на файл, пять секунд SQL на источник, read-only транзакция. Ошибка аналитики не участвует в пути подключения.

Закрытый HTML-снимок открывается проектом как локальный файл с правами 0600 вне webroot. Это диагностический MVP, **не постоянно обновляемый веб-дашборд**. Новая схема отчёта экспериментальная, не клиентский контракт. Сырые строки версий проходят строгий фильтр номеров; неизвестные значения объединяются. Выход не содержит email, ID, ключей, IP, имён компьютеров, назначения сеансов или их содержимого.

## Целевая архитектура после принятия

Самый простой следующий шаг — периодическое обновление агрегированного снимка из копий, а не Prometheus/Grafana/ClickHouse. Частоту начать с одного раза в сутки; отдельный cron и формат хранения требуют принятия этого ADR и ревью. Использовать Core и существующую SQLite; отдельную БД, контейнер, домен или VPS не вводить. VPN и соседние сайты не менять; маршрут аналитики добавлять только патчем блока desk.funti.cc из infra/funtidesk-account/ после ревью архитектора.

Закрытый FuntiDesk Analytics: дневные ряды аккаунтов, активности, попыток/результатов, качества, версий; у каждой панели источник, охват, время свежести и неизвестные значения. До появления источника показывать «нет данных», а не 0. Для веб-доступа нужен отдельный явно разрешённый администратор, аутентификация и авторизация каждого запроса; обычная почтовая сессия кабинета доступа не даёт. Отрицательные тесты: анонимный/обычный аккаунт → 401/403, прямой URL данных закрыт. Уточнение владельца 2026-11-10: целевой интерфейс — HTTPS на существующем desk.funti.cc, отдельный непубликуемый путь и пароль, без обязательного SSH-туннеля. Скрытый путь не заменяет аутентификацию. Простейший вариант — существующий Caddy с Basic Auth и отдельным административным логином; хранить только стойкий хеш пароля в закрытой серверной конфигурации, секрет не передавать через URL и не коммитить. Защитить весь префикс, включая HTML, JSON и вспомогательные файлы; закрытый файл не должен быть доступен через альтернативный file_server. Добавить Cache-Control: no-store и X-Robots-Tag: noindex, nofollow; не включать ссылку в публичную навигацию. Проверить отсутствие обхода через иной путь, вложенные файлы и обычную сессию кабинета. При отсутствии конфигурации авторизации доступ запрещён. Конкретный путь и пароль задаются приватно при настройке, не в публичных Issues или PR. Применение Caddy-патча и production-проверка остаются после ревью; локальный снимок — подготовительный инструмент, не конечный пользовательский интерфейс.

## Определения и идентичность

- Установка — локальная идентичность инсталляции, пока не измеряется. Переустановка/клонирование могут менять/копировать идентичность.
- Аккаунт — текущая строка `accounts`; человек может иметь несколько аккаунтов, несколько людей — общий компьютер.
- Устройство кабинета — уникальный `pk` среди текущих привязок; hbbs — отдельно число ID и непустых ключей. Между источниками счётчики не складывать.
- Активность кабинета за N дней — `now-N*86400 < last_seen <= now`, уникальный ключ; это обращения кабинета, не все работающие клиенты и не успешные подключения.
- Активный аккаунт — уникальный account_id таких устройств. Не называть активным человеком.
- История — сохранённые сообщения клиентов, дедупликация `(account_id,event_id)`. Импорт старой локальной истории не является новым сеансом. История ограничена 1000 записями на аккаунт, 90 днями и пользовательской очисткой.
- Уникальные люди без отдельного исследования не измеряются.

## Необязательная телеметрия — следующий отдельный этап

Сначала явное согласие в клиенте, по умолчанию выключено; отключение прекращает очередь/отправку и удаляет локальные ожидающие события. Нельзя связать обязательную регистрацию hbbs или работу соединений с согласием. Существующие клиенты ничего нового не отправляют и продолжают работать.

Предлагаемые события: случайный session_event_id на попытку и завершающий результат с тем же ID; транспорт p2p/relay/unknown, ограниченный код результата, версия/платформа, длительность handshake и округлённые показатели качества. Без адресата, IP, email, путей, файлов, паролей, экрана и произвольного текста. При повторах уникальность `(installation_pseudonym,event_id,kind)`, обновление результата один раз; один выбранный отправитель на сеанс, чтобы стороны не удваивали счётчик. Ограниченная очередь и best-effort отправка после подключения, таймаут и лимит размера; отказ API ничего не блокирует. Псевдоним — HMAC локальной идентичности с отдельным ключом, не сырой ID; ротация разрывает долгосрочный анализ и должна учитываться в метриках. Ключи только в secrets.

Успешность = подтверждённый защищённый сеанс / завершённые попытки в согласованной когорте; незавершённые и просроченные попытки отдельно, таймаут результата заранее фиксируется. P2P/relay — только среди успешных с известным транспортом. Качество — p50/p95 handshake и доля ошибок с размером выборки. Эти метрики относятся только к согласившейся когорте, не ко всем пользователям.

## Хранение и удаление

Предложение: новые сырые события и дедупликационные ключи 30 дней, дневные агрегаты 13 месяцев, диагностические HTML-снимки семь дней; согласованные копии удалить сразу после анализа в закрытом хранилище. Не сохранять analytics в публичных Actions artifacts, Issues, Telegram или Git. У существующей истории остаются 90 дней/1000 записей; MVP ничего не удаляет и сроки production не меняет. Сроки, удаление по отзыву согласия и резервные копии должны быть реализованы и протестированы до сбора событий. Малые когорты не публиковать.

## Приёмка и ограничения

MVP: тесты v4/v5, границ времени, read-only, фильтрации, неизвестной схемы, отсутствующего файла и прав отчёта. Совместимость обеспечена отсутствием изменений рабочих компонентов; реальная E2E не выполнена. Динамику прошлой DAU нельзя восстановить по одному last_seen. Для полного дашборда нужны наблюдения во времени; новые события и веб-доступ — отдельные небольшие PR после ревью.
