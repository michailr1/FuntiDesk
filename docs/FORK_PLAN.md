# Стратегия форка RustDesk и следующая история

Статус: предложение к решению владельца проекта. Основано на фактической проверке
upstream-кода на зафиксированных в `docs/UPSTREAM.md` baseline-версиях.

## 1. Что показала проверка upstream

Проверка выполнена на `rustdesk/rustdesk@6c57829` (1.4.9),
`rustdesk/rustdesk-server@73523b3` (1.1.16) и их submodule `hbb_common`.

### 1.1 Репозиториев три, а не два

`libs/hbb_common` — отдельный репозиторий `rustdesk/hbb_common`, подключённый как
git submodule и к клиенту, и к серверу, причём **на разных коммитах**:

```text
client 1.4.9   -> libs/hbb_common @ 7e1c392c62d39c364127307cd408421dd5f8cfb0
server 1.1.16  -> libs/hbb_common @ 83419b6549636ee39dacef7776c473f5802e08d6
```

Это не деталь сборки. Именно в `hbb_common/src/config.rs` лежит вся идентификация
инфраструктуры, то есть основной предмет нашего форка.

### 1.2 Адрес и ключ публичной инфраструктуры зашиты в код

`hbb_common/src/config.rs`:

```rust
pub const RENDEZVOUS_SERVERS: &[&str] = &["rs-ny.rustdesk.com"];
pub const RS_PUB_KEY: &str = "OeVuKk5nlHiXp+APNn0Y3pC1Iwpwn44JGqrQCsWqmBw=";
```

`Config::get_rendezvous_server()` перебирает пять источников по порядку: имя exe-файла,
опция `custom-rendezvous-server`, `PROD_RENDEZVOUS_SERVER`, сохранённый конфиг и, если
всё пусто, — константу с публичным сервером. Последняя ступень означает, что сборка
без правки кода **всегда** имеет работающий путь на чужую инфраструктуру. Это прямо
противоречит требованию fail closed из `docs/ARCHITECTURE.md`.

Вывод: конфигурацией задачу не решить, правка исходного кода обязательна.

### 1.3 Механизм custom client подписан чужим ключом

`src/common.rs:read_custom_client()` читает `custom.txt`, но перед применением
проверяет подпись жёстко зашитым публичным ключом RustDesk
(`5Qbwsde3unUcJBtrx9ZkvUmwFNoExHzpryHuPUdqlWM=`). Подписанный этим ключом файл может
переопределить `app-name`, `default-settings` и `override-settings`.

То есть в неизменённой сборке существует канал конфигурации, ключ от которого
принадлежит не нам. Для FuntiDesk это вопрос модели доверия, а не брендинга: канал
нужно либо переключить на наш ключ, либо убрать полностью. Требуется ADR.

### 1.4 Обращения к внешним сервисам

- проверка обновлений: `https://api.rustdesk.com/version/latest`;
- web-console по умолчанию: `https://admin.rustdesk.com`;
- в `src/client.rs` и `src/lang/*` — ссылки на документацию rustdesk.com.

### 1.5 Брендинг дешевле, чем кажется

Из 1182 вхождений строки `RustDesk` в Rust-коде 1107 находятся в `src/lang/*.rs`,
то есть в файлах локализации, и только 75 — в собственно коде, где это большей частью
идентификаторы (`RustDeskInterval`, `RUSTDESK_IDD_DEVICE_STRING`, имена драйверов и
служб) и комментарии.

Практический вывод: пользовательский текст меняется правкой языковых файлов,
а идентификаторы кода трогать не нужно и вредно — они увеличивают конфликты при
обновлении upstream. `src/lang/ru.rs` уже существует (769 строк), что совпадает
с решением о русском языке как основном.

### 1.6 Масштаб и стоимость сборки

- Rust: 250 файлов `.rs` в клиенте.
- Flutter: ~71 000 строк Dart в `flutter/lib`.
- Legacy UI на Sciter (`src/ui/*.tis`, зависимость `sciter-rs`) присутствует
  параллельно с Flutter.
- Нативные зависимости через vcpkg: `aom`, `ffmpeg`, `libvpx`, `libyuv`, `opus`,
  `libjpeg-turbo`, `mfx-dispatch`, с закреплённым baseline реестра.
- Версия Flutter закреплена в CI, включая патч под конкретную версию.

Главный технический риск ближайших этапов — не код, а воспроизводимая сборка Windows.

### 1.7 Лицензия

Обе кодовые базы под **AGPL-3.0**. Раздача сборок семье и друзьям является
распространением, поэтому получателям должен быть доступен полный исходный код
именно нашей модификации, включая скрипты сборки. Это совместимо с целями проекта,
но должно быть зафиксировано отдельным решением, а не подразумеваться.

## 2. Предлагаемое решение по структуре репозитория

Монорепо с тремя импортированными деревьями:

```text
/client          # rustdesk 1.4.9
/client/libs/hbb_common   # hbb_common @ 7e1c392
/server          # rustdesk-server 1.1.16
/server/libs/hbb_common   # hbb_common @ 83419b6
/docs
/infra
```

**`hbb_common` импортируется дважды, каждое дерево на своём upstream-пине.**

Обоснование: сведение двух пинов к одному — это изменение ядра сразу двух продуктов
ради эстетики структуры. Оно не требуется ни для M1, ни для M2, зато создаёт риск
рассинхронизации протокола между нашим клиентом и нашим сервером. Дублирование стоит
дёшево, потому что наши правки идентификации инфраструктуры применяются только
к клиентской копии: у сервера своя конфигурация. Унификацию можно рассмотреть
позже, отдельным решением с явной выгодой.

Почему не альтернативы:

- **submodule на upstream** — production-сборка зависела бы от чужого репозитория
  и не была бы воспроизводима из нашего, что противоречит правилу 8 в `AGENTS.md`;
- **три отдельных форк-репозитория** — разъезжаются пины, ревью и релизы; для команды
  такого размера накладные расходы выше пользы;
- **copy-paste снапшот** — теряется история upstream и возможность переносить
  security fixes, что противоречит `docs/UPSTREAM.md`.

Импорт выполняется history-preserving способом (`git subtree add --prefix=...`),
upstream-remote'ы настраиваются по `docs/UPSTREAM.md`.

## 3. Минимальный patch set FuntiDesk

Принцип: правок мало, они сосредоточены в предсказуемых местах, каждая объяснена.

| # | Где | Что | Зачем |
|---|-----|-----|-------|
| P1 | `client/libs/hbb_common/src/config.rs` | `RENDEZVOUS_SERVERS`, `RS_PUB_KEY` — наши значения | привязка к инфраструктуре FuntiDesk |
| P2 | там же, `get_rendezvous_server(...)` | убрать ступени, ведущие к чужой или задаваемой пользователем инфраструктуре в production-сборке | fail closed |
| P3 | `client/src/common.rs` | `read_custom_client`: наш ключ подписи либо удаление механизма | устранение чужого канала конфигурации |
| P4 | `client/src/common.rs` | update-check и web-console URL | отсутствие скрытых обращений вовне |
| P5 | `client/src/lang/*.rs`, `res/`, `flutter/` | пользовательский текст, иконки, имя приложения | продуктовая идентичность |
| P6 | `client/Cargo.toml`, `client/src/ui/` | удаление Sciter UI | сокращение поверхности сопровождения |

P1–P4 — это security-периметр, они обязательны до любой раздачи сборок.
P5–P6 — продуктовый слой, они могут идти позже.

Каждая правка сопровождается комментарием-маркером в коде, чтобы при merge upstream
было видно, что это наше намеренное расхождение, а не случайный конфликт.

## 4. Следующая история: импорт форка

Цель истории — **получить у себя в репозитории неизменённый upstream, который
воспроизводимо собирается**. Ни брендинга, ни правок конфигурации в этой истории нет.

Причина именно такого порядка: пока сборка не воспроизводится, любая наша правка
неотличима от поломки, унаследованной от upstream.

### FD-1. Импорт трёх деревьев

- настроить `upstream-client`, `upstream-server`, `upstream-common`;
- `git subtree add` для `/client`, `/server` и двух копий `hbb_common` на пинах из §2;
- зафиксировать в `docs/UPSTREAM.md` все три baseline, включая `hbb_common`.

Приёмка: история upstream присутствует в репозитории; рабочее дерево побайтно
совпадает с соответствующими upstream-коммитами; сборка ещё не проверяется.

### FD-2. Воспроизводимая сборка сервера

- сборка `hbbs`/`hbbr` из `/server` по документированной процедуре.

Приёмка: бинарники собираются из нашего репозитория; процедура записана в `/infra`.

### FD-3. Воспроизводимая сборка клиента Windows

- закрепить версии Rust, Flutter и vcpkg-baseline;
- собрать неизменённый клиент из `/client`.

Приёмка: получен работоспособный Windows-бинарник из нашего репозитория.
Допускается, что он на этом этапе ещё называется и ведёт себя как upstream.

### FD-4. Фиксация решений

ADR по трём вопросам, которые нельзя оставлять неявными:
доверие к custom-client-каналу (§1.3), обязательства AGPL (§1.7),
политика повторного импорта `hbb_common` (§2).

Приёмка: решения записаны, `docs/ARCHITECTURE.md` обновлён.

### Вне этой истории

Брендинг, собственный UX, привязка к нашим серверам, installer, подпись релизов,
Android и iOS. Они начинаются после того, как сборка стала воспроизводимой,
и после M1, потому что для привязки клиента нужны реальные адрес и ключ сервера.

## 5. Требуются решения владельца

1. Принять структуру с двойным импортом `hbb_common` (§2) либо потребовать унификации.
2. Судьба механизма custom client (§1.3): свой ключ подписи или удаление.
3. Готовность выполнять обязательства AGPL при раздаче сборок (§1.7).
4. Судьба Sciter UI: удалить в рамках форка или оставить нетронутым.
