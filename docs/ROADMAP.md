# План развития FuntiDesk

## M0 — Архитектура

- Зафиксировать baseline клиента и сервера.
- Определить стратегию синхронизации с upstream.
- Определить trust model и security baseline.
- Зафиксировать продуктовую идентичность и правила отделения интерфейса.
- Определить границы лицензирования и атрибуции.
- Принять ADR по структуре импорта, custom-client trust и AGPL distribution policy.

Критерий завершения: архитектурные и security-решения задокументированы, реализацию можно начинать без незакрытых вопросов по модели доверия.

## M0.5 — Импорт исходников и эталонная сборка

Это обязательный технический этап между архитектурой и нашими изменениями.

- Импортировать клиент 1.4.9 в `/client` с сохранением истории.
- Импортировать `hbb_common@7e1c392...` в `/client/libs/hbb_common` как обычное дерево исходников.
- Импортировать сервер 1.1.16 в `/server` с сохранением истории.
- Импортировать `hbb_common@83419b6...` в `/server/libs/hbb_common` как отдельную копию.
- Зафиксировать toolchain: Rust, Flutter, vcpkg baseline и необходимые Windows build dependencies.
- Воспроизвести **неизменённую upstream Windows-сборку** из нашего монорепозитория.
- Сохранить build log и контрольные сведения об артефакте.

Критерий завершения: чистый baseline собирается повторяемо из `michailr1/FuntiDesk` без наших функциональных изменений. До этого этапа запрещено считать ошибки будущих FuntiDesk-патчей нашими или upstream-проблемами без дополнительной проверки.

## M1 — Self-hosted Server

- Воспроизводимое развёртывание rendezvous/relay.
- Постоянные ключи и конфигурация.
- Документация по портам и firewall.
- Health checks и логи.
- Backup/restore server identity material.
- Получить реальные production hostname и public key сервера для следующего этапа клиента.

Критерий завершения: сервер может быть восстановлен по документации репозитория, имеет стабильную server identity и готов предоставить клиенту закрепляемые endpoint/public key.

## M2 — Windows MVP

- Первая Windows-сборка FuntiDesk.
- Инфраструктура FuntiDesk преднастроена.
- Удалён публичный rendezvous/public-key fallback из client `hbb_common`.
- `custom-client` канал отключён в production.
- Нет скрытого fallback на стороннюю публичную инфраструктуру.
- Числовой ID устройства сохраняется.
- Работают удалённое управление, буфер обмена и передача файлов.
- Есть portable и установленный/service режимы.

Критерий завершения: два Windows-клиента могут соединиться через инфраструктуру FuntiDesk, а ошибочная конфигурация fail closed.

## M3 — End-to-End Validation

- Политика обновления сервера: отслеживание security-релизов `rustdesk-server`, контролируемое обновление image digest и проверенный rollback.
- Внешний мониторинг доступности `21115/tcp`, `21116/tcp+udp`, `21117/tcp` с уведомлением владельца. Сделано 2026-10-14: `server-monitor.yml`, раз в 10 минут, issue `server-down` при сбое (`docs/SERVER_DEPLOYMENT.md`, «Внешний мониторинг»); `udp/21116` не проверяется.
- Измерение relay-трафика и проверка лимитов канала/трафика текущего VPS.
- Прямой P2P-маршрут.
- Relay fallback.
- Разные NAT/провайдеры.
- Перезапуск и повторное подключение.
- Windows login screen/UAC.
- Буфер обмена и передача файлов.
- Временный и постоянный доступ.
- Проверка отсутствия неожиданных внешних endpoint.

Критерий завершения: вся матрица приёмки проходит без зависимости от сторонних публичных rendezvous/relay-сервисов.

## M4 — Family Release

- Минимальный канал обновлений: клиент умеет показать, что доступна новая версия; документирована ручная процедура обновления с проверкой SHA256/подписи. Полноценное auto-update проектируется отдельным ADR после Family Release.
- **Обновление кнопкой** (идея владельца 2026-10-09). В клиенте — «Проверить обновления» / «Обновить»: та же цепочка, что `install.ps1` (последний релиз, проверка SHA256, замена файлов, перезапуск с тем же профилем), без PowerShell. **Удалённое обновление**: при подключении клиент сравнивает версию той стороны с последним релизом; если там старая — в окне сеанса «На той стороне старая версия FuntiDesk» с кнопкой «Обновить», тот компьютер сам скачивает и ставит релиз и сеанс переподключается (решение владельца 2026-10-09: без подтверждения на той стороне, чтобы не дёргать человека; помощник в сеансе управления и так может установить что угодно). Предварительно — своя нумерация сборок: сделано 2026-10-11, версия для людей `1.4.9-ft.<N>`, где `N` — число коммитов до собранного (`git rev-list --count HEAD`, `client/build.rs` → `FUNTI_BUILD`; одинаково на всех платформах и воспроизводимо из репозитория, CI берёт полную историю; `0` — номер неизвестен). Видна в «О программе», в строке состояния главного экрана и в `--version`. Версия протокола `crate::VERSION` остаётся `1.4.9`: по ней upstream проверяет возможности другой стороны и пишет реестр установщика. Модель доверия — `docs/ADR-007-updates.md` (решение владельца 2026-10-11: пока без подписи релизов, как `install.ps1` — только релизы FuntiDesk по HTTPS, проверка SHA256, двухфакторный вход на GitHub; подпись ключом вне GitHub — путь усиления), fail closed при любой ошибке; на той стороне — видимое без кнопок «FuntiDesk обновляется, сейчас переподключимся» (без скрытых действий, SECURITY.md); служба (установленный режим) обновляется так же. Этап 1 сделан 2026-10-11: «Проверить обновления» / «Обновить» в «О программе» для копии `install.ps1` (ADR-007, «Реализация»); дальше — служба и удалённое обновление из сеанса. Этап 1 проверен 2026-10-12 на опубликованном релизе (`1.4.9-ft.12403` → `1.5.0-ft.12803`). Служба (установленный режим) — этап 2 сделан и проверен 2026-10-14 (ADR-007, «Этап 2», PR #38; `docs/reviews/2026-10-14-service-update-acceptance.md`). Этап 3 — обновление другого компьютера из сеанса — сделан 2026-10-17 и принят владельцем 2026-10-18 (ADR-007, «Этап 3»; `docs/reviews/2026-10-18-remote-update-acceptance.md`).
- **Оповещение о новой версии** (замечание владельца 2026-10-12). Сейчас о новой версии можно узнать, только нажав «Проверить обновления» в «О программе». Нужно ненавязчивое окошко на главном экране: «Вышла новая версия FuntiDesk 1.5.0-ft.N» с кнопками «Обновить» и «Позже»; не модальное, не перекрывает работу, «Позже» скрывает его до следующей версии. Нажатие на окошко раскрывает его и показывает, что нового в версии (замечание владельца 2026-10-12): текст — верхний раздел `docs/WHATS_NEW.md`, CI кладёт его в релиз файлом `funtidesk-whats-new.txt`. Сделано 2026-10-13 (ADR-007, «Любая копия», PR #24); старые `FuntiDesk-portable.exe` нужно один раз скачать заново. - ✅ Звонящему показывать «Камера на той стороне недоступна» (камера без кадров, запрет антивируса или политики) вместо бесконечного «ожидания изображения» (найдено 2026-10-09); сделано в коде 2026-10-11 (ADR-005, «Последствия»), ждёт проверки на живых компьютерах. Проверено 2026-10-11 (minipc без камеры, разные версии) — PASS.
- ✅ Доработки звонков и главного экрана (найдено на проверке 2026-10-08, сделано 2026-10-09): звонящему «Абонент отклонил звонок»; мелодия входящего звонка; «Показывать картинку на главном экране» в настройках возвращает скрытую картинку; при ошибке рукопожатия прямого соединения (`peer did not send SignedId`) — переход на relay (`a03ad2f`).

Разовое сопряжение по коду из 6 цифр, дальше звонки и подключения без пароля с «Принять» на той стороне; список семьи хранится на каждом устройстве. - ✅ **Проще добавлять в семью** (замечание владельца 2026-10-11; сделано и проверено 2026-10-12, ADR-008: только код, общий лимит неверных кодов на сервере, дефект сопряжения исправлен). По решению владельца не разбирать отдельно, а проверить на новом механизме добавления по коду; при повторе — журнал ноутбука (`%APPDATA%\FuntiDesk\log`).
- ✅ **«Попросить помощи»** (решение владельца 2026-10-08, приоритетная собственная функция). На компьютере члена семьи — одна заметная кнопка; помощник получает уведомление «Мама просит помощи» с кнопкой «Подключиться» и подключается без диктовки ID и пароля. Требования до проектирования (нужен ADR): Статус: сделано и принято 2026-10-09 (ADR-006, этап 2).
  - канал уведомлений — инфраструктура FuntiDesk; сторонний мессенджер допустим только явным решением владельца, без скрытого fallback;
  - помощник заранее и явно связан с компьютером (разовое сопряжение); запрос уходит только связанным помощникам;
  - передаётся только ID и свежий одноразовый пароль с ограниченным сроком; постоянный доступ запрос не включает и не раскрывает;

  - если канал недоступен — fail closed: сообщение об ошибке и обычный путь «продиктуйте ID и пароль»;
  - до мобильных клиентов помощник получает запрос в Windows-клиенте.

API и миграция v5 влиты в #71: отмена действует только для компьютеров, привязанных позже; прежние доставки/ACK остаются, права семьи не восстанавливаются. UI Windows/веб принят в #72: подтверждение «Отменить удаление», статус с датой и прежние строки доставки. Требуются merge и проверка на реальных клиентах. На desk ещё не применено.

**Восстановление телефонной вкладки, уточнение владельца 2026-10-18:** подготовлен PR для одной автоматической попытки в течение пяти минут после сворачивания/обрыва и системного автозаполнения постоянного пароля. Производное пароля остаётся только в RAM той же вкладки; новые подписи/handshake/challenge и права проверяются заново. Уточнение ADR-012/014 и код приняты, #76 влит и выложен из main `5ba366985db8`. Все 25 публичных файлов, оба WSS-маршрута, мобильная разметка и атрибуты автозаполнения проверены; API/SQLite v4 сохранены. Реальные блокировка iPhone и предложение Safari ещё требуют проверки владельцем. [Поставка](reviews/2026-10-18-phone-web-deploy.md).

**Слежение за курсором на телефоне, уточнение владельца 2026-10-18:** подготовлено автоматическое центрирование увеличенного экрана при движении курсора в тачпаде. Прокрутка ограничена рабочим столом, учитывает клавиатуру и поворот; ручное перемещение двумя пальцами и прямое касание сохранены. Шифрованная браузерная проверка покрывает движение/drag, границы, fit, прямое касание и доступную область. Принято в #77 и выложено вместе с #78 из main `6277d1b4431a`. Публичные файлы/WSS и совместный Chromium-сценарий проверены; нужна реальная проверка iPhone. [Поставка](reviews/2026-10-18-phone-web-deploy.md).

**Восстановление после reload, запрос владельца 2026-10-18:** приняты архитектором реализация и уточнение ADR-012/014: одна попытка в той же телефонной вкладке по записи sessionStorage с клиентским сроком до пяти минут, удаляемой до handshake. Запись создаётся только при pagehide подтверждённого сеанса; новый секрет эквивалентен паролю для соли и доступен коду origin, это не серверный TTL. Принято в #78: расширение срока/хранилища/устройств — только через новый ADR. #77/#78 влиты и выложены вместе из main `6277d1b4431a`, API/SQLite v4 сохранены. Настоящий reload проверен в шифрованном локальном сценарии; на публичной странице проверены файлы, очистка плохой записи и WSS. Реальный iPhone проверяет владелец. [Поставка](reviews/2026-10-18-phone-web-deploy.md).

**Повторная жалоба на восстановление Safari, 2026-10-18:** владелец сообщает возврат к исходной форме без ошибки после reload/фона с постоянным паролем. На публичном desk подтверждён bundle `6277d1b44`. Обычный reload и короткий обрыв проходят в Chromium и локальном WebKit 27.2; точная причина на физическом iPhone пока не подтверждена. Подготовлена совместимость с legacy Navigation Timing, когда modern entry отсутствует, и сообщения о недоступном/потерянном/истёкшем восстановлении и возврате BFCache. WebKit-проверка с отключённым modern entry падает на main и проходит с правкой. Legacy-проверка принята в #80; по ревью сообщения ограничены подтверждённым предыдущим сеансом (несекретная метка времени для reload и RAM-признак для BFCache). Нужны повторное ревью, выкладка и подтверждение на том же iPhone; жалоба ещё не закрыта.
