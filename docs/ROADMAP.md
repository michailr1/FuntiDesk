# План развития FuntiDesk

## M0 — Архитектура

- Зафиксировать baseline клиента и сервера.
- Определить стратегию синхронизации с upstream.
- Определить trust model и security baseline.
- Зафиксировать продуктовую идентичность и правила отделения интерфейса.
- Определить границы лицензирования и атрибуции.
- Принять ADR по структуре импорта, custom-client trust и AGPL distribution policy.

Критерий завершения: архитектурные и security-решения задокументированы, реализацию можно начинать без незакрытых вопросов по модели доверия.

## M0.5 — Импорт исходников и эталонная сборка

Это обязательный технический этап между архитектурой и нашими изменениями.

- Импортировать клиент 1.4.9 в `/client` с сохранением истории.
- Импортировать `hbb_common@7e1c392...` в `/client/libs/hbb_common` как обычное дерево исходников.
- Импортировать сервер 1.1.16 в `/server` с сохранением истории.
- Импортировать `hbb_common@83419b6...` в `/server/libs/hbb_common` как отдельную копию.
- Зафиксировать toolchain: Rust, Flutter, vcpkg baseline и необходимые Windows build dependencies.
- Воспроизвести **неизменённую upstream Windows-сборку** из нашего монорепозитория.
- Сохранить build log и контрольные сведения об артефакте.

Критерий завершения: чистый baseline собирается повторяемо из `michailr1/FuntiDesk` без наших функциональных изменений. До этого этапа запрещено считать ошибки будущих FuntiDesk-патчей нашими или upstream-проблемами без дополнительной проверки.

## M1 — Self-hosted Server

- Воспроизводимое развёртывание rendezvous/relay.
- Постоянные ключи и конфигурация.
- Документация по портам и firewall.
- Health checks и логи.
- Backup/restore server identity material.
- Получить реальные production hostname и public key сервера для следующего этапа клиента.

Критерий завершения: сервер может быть восстановлен по документации репозитория, имеет стабильную server identity и готов предоставить клиенту закрепляемые endpoint/public key.

## M2 — Windows MVP

- Первая Windows-сборка FuntiDesk.
- Инфраструктура FuntiDesk преднастроена.
- Удалён публичный rendezvous/public-key fallback из client `hbb_common`.
- `custom-client` канал отключён в production.
- Нет скрытого fallback на стороннюю публичную инфраструктуру.
- Числовой ID устройства сохраняется.
- Работают удалённое управление, буфер обмена и передача файлов.
- Есть portable и установленный/service режимы.

Критерий завершения: два Windows-клиента могут соединиться через инфраструктуру FuntiDesk, а ошибочная конфигурация fail closed.

## M3 — End-to-End Validation

- Политика обновления сервера: отслеживание security-релизов `rustdesk-server`, контролируемое обновление image digest и проверенный rollback.
- Внешний мониторинг доступности `21115/tcp`, `21116/tcp+udp`, `21117/tcp` с уведомлением владельца. Сделано 2026-10-14: `server-monitor.yml`, раз в 10 минут, issue `server-down` при сбое (`docs/SERVER_DEPLOYMENT.md`, «Внешний мониторинг»); `udp/21116` не проверяется.
- Измерение relay-трафика и проверка лимитов канала/трафика текущего VPS.
- Прямой P2P-маршрут.
- Relay fallback.
- Разные NAT/провайдеры.
- Перезапуск и повторное подключение.
- Windows login screen/UAC.
- Буфер обмена и передача файлов.
- Временный и постоянный доступ.
- Проверка отсутствия неожиданных внешних endpoint.

Критерий завершения: вся матрица приёмки проходит без зависимости от сторонних публичных rendezvous/relay-сервисов.

## M4 — Family Release

- Минимальный канал обновлений: клиент умеет показать, что доступна новая версия; документирована ручная процедура обновления с проверкой SHA256/подписи. Полноценное auto-update проектируется отдельным ADR после Family Release.
- **Обновление кнопкой** (идея владельца 2026-10-09). В клиенте — «Проверить обновления» / «Обновить»: та же цепочка, что `install.ps1` (последний релиз, проверка SHA256, замена файлов, перезапуск с тем же профилем), без PowerShell. **Удалённое обновление**: при подключении клиент сравнивает версию той стороны с последним релизом; если там старая — в окне сеанса «На той стороне старая версия FuntiDesk» с кнопкой «Обновить», тот компьютер сам скачивает и ставит релиз и сеанс переподключается (решение владельца 2026-10-09: без подтверждения на той стороне, чтобы не дёргать человека; помощник в сеансе управления и так может установить что угодно). Предварительно — своя нумерация сборок: сделано 2026-10-11, версия для людей `1.4.9-ft.<N>`, где `N` — число коммитов до собранного (`git rev-list --count HEAD`, `client/build.rs` → `FUNTI_BUILD`; одинаково на всех платформах и воспроизводимо из репозитория, CI берёт полную историю; `0` — номер неизвестен). Видна в «О программе», в строке состояния главного экрана и в `--version`. Версия протокола `crate::VERSION` остаётся `1.4.9`: по ней upstream проверяет возможности другой стороны и пишет реестр установщика. Модель доверия — `docs/ADR-007-updates.md` (решение владельца 2026-10-11: пока без подписи релизов, как `install.ps1` — только релизы FuntiDesk по HTTPS, проверка SHA256, двухфакторный вход на GitHub; подпись ключом вне GitHub — путь усиления), fail closed при любой ошибке; на той стороне — видимое без кнопок «FuntiDesk обновляется, сейчас переподключимся» (без скрытых действий, SECURITY.md); служба (установленный режим) обновляется так же. Этап 1 сделан 2026-10-11: «Проверить обновления» / «Обновить» в «О программе» для копии `install.ps1` (ADR-007, «Реализация»); дальше — служба и удалённое обновление из сеанса. Этап 1 проверен 2026-10-12 на опубликованном релизе (`1.4.9-ft.12403` → `1.5.0-ft.12803`). Служба (установленный режим) — этап 2 сделан и проверен 2026-10-14 (ADR-007, «Этап 2», PR #38; `docs/reviews/2026-10-14-service-update-acceptance.md`). - ✅ **Семейный доступ** (решение владельца 2026-10-08, `docs/ADR-006-family-access.md`). Разовое сопряжение по коду из 6 цифр, дальше звонки и подключения без пароля с «Принять» на той стороне; список семьи хранится на каждом устройстве. Этап 1 — сопряжение и вход; этап 2 — «Попросить помощи» на том же механизме. Статус 2026-10-12: этапы 1–2 приняты; добавление по одному коду — ADR-008.
- ✅ **Проще добавлять в семью** (замечание владельца 2026-10-11; сделано и проверено 2026-10-12, ADR-008: только код, общий лимит неверных кодов на сервере, дефект сопряжения исправлен). Сейчас вводят ID и код из 6 цифр и имя. Нужно: одно поле, куда вставляется «код и ID» (кнопка «Скопировать код и ID» уже есть) или вводится код; имя по умолчанию — имя компьютера той стороны, можно изменить. Решение владельца 2026-10-11: вводят **только код**, компьютер находится по коду на сервере FuntiDesk; код живёт 3–5 минут и подходит один раз. Нужно: изменение сервера и протокола (свои поля от 1000), защита от перебора (ограничение попыток на адрес и на код), дополнение ADR-006; до этого — одно поле «код и ID». **Дефект (2026-10-11):** при вводе кода на ноутбуке владельца (`440171008`, сборки `12397` и `12400`) компьютер, показавший код (minipc), добавляет ноутбук, а ноутбук показывает «добавлен», но в его списке семьи запись не появляется, и после перезапуска тоже. Ожидание подтверждения от службы (`51863d3`) не помогло. По решению владельца не разбирать отдельно, а проверить на новом механизме добавления по коду; при повторе — журнал ноутбука (`%APPDATA%\FuntiDesk\log`).
- ✅ **«Попросить помощи»** (решение владельца 2026-10-08, приоритетная собственная функция). На компьютере члена семьи — одна заметная кнопка; помощник получает уведомление «Мама просит помощи» с кнопкой «Подключиться» и подключается без диктовки ID и пароля. Требования до проектирования (нужен ADR): Статус: сделано и принято 2026-10-09 (ADR-006, этап 2).
  - канал уведомлений — инфраструктура FuntiDesk; сторонний мессенджер допустим только явным решением владельца, без скрытого fallback;
  - помощник заранее и явно связан с компьютером (разовое сопряжение); запрос уходит только связанным помощникам;
  - передаётся только ID и свежий одноразовый пароль с ограниченным сроком; постоянный доступ запрос не включает и не раскрывает;
  - отправитель видит, кому ушёл запрос и кто подключился, и может отменить запрос;
  - если канал недоступен — fail closed: сообщение об ошибке и обычный путь «продиктуйте ID и пароль»;
  - до мобильных клиентов помощник получает запрос в Windows-клиенте.
