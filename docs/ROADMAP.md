# План развития FuntiDesk

## M0 — Архитектура

- Зафиксировать baseline клиента и сервера.
- Определить стратегию синхронизации с upstream.
- Определить trust model и security baseline.
- Зафиксировать продуктовую идентичность и правила отделения интерфейса.
- Определить границы лицензирования и атрибуции.
- Принять ADR по структуре импорта, custom-client trust и AGPL distribution policy.

Критерий завершения: архитектурные и security-решения задокументированы, реализацию можно начинать без незакрытых вопросов по модели доверия.

## M0.5 — Импорт исходников и эталонная сборка

Это обязательный технический этап между архитектурой и нашими изменениями.

- Импортировать клиент 1.4.9 в `/client` с сохранением истории.
- Импортировать `hbb_common@7e1c392...` в `/client/libs/hbb_common` как обычное дерево исходников.
- Импортировать сервер 1.1.16 в `/server` с сохранением истории.
- Импортировать `hbb_common@83419b6...` в `/server/libs/hbb_common` как отдельную копию.
- Зафиксировать toolchain: Rust, Flutter, vcpkg baseline и необходимые Windows build dependencies.
- Воспроизвести **неизменённую upstream Windows-сборку** из нашего монорепозитория.
- Сохранить build log и контрольные сведения об артефакте.

Критерий завершения: чистый baseline собирается повторяемо из `michailr1/FuntiDesk` без наших функциональных изменений. До этого этапа запрещено считать ошибки будущих FuntiDesk-патчей нашими или upstream-проблемами без дополнительной проверки.

## M1 — Self-hosted Server

- Воспроизводимое развёртывание rendezvous/relay.
- Постоянные ключи и конфигурация.
- Документация по портам и firewall.
- Health checks и логи.
- Backup/restore server identity material.
- Получить реальные production hostname и public key сервера для следующего этапа клиента.

Критерий завершения: сервер может быть восстановлен по документации репозитория, имеет стабильную server identity и готов предоставить клиенту закрепляемые endpoint/public key.

## M2 — Windows MVP

- Первая Windows-сборка FuntiDesk.
- Инфраструктура FuntiDesk преднастроена.
- Удалён публичный rendezvous/public-key fallback из client `hbb_common`.
- `custom-client` канал отключён в production.
- Нет скрытого fallback на стороннюю публичную инфраструктуру.
- Числовой ID устройства сохраняется.
- Работают удалённое управление, буфер обмена и передача файлов.
- Есть portable и установленный/service режимы.

Критерий завершения: два Windows-клиента могут соединиться через инфраструктуру FuntiDesk, а ошибочная конфигурация fail closed.

## M3 — End-to-End Validation

- Политика обновления сервера: отслеживание security-релизов `rustdesk-server`, контролируемое обновление image digest и проверенный rollback.
- Внешний мониторинг доступности `21115/tcp`, `21116/tcp+udp`, `21117/tcp` с уведомлением владельца.
- Измерение relay-трафика и проверка лимитов канала/трафика текущего VPS.
- Прямой P2P-маршрут.
- Relay fallback.
- Разные NAT/провайдеры.
- Перезапуск и повторное подключение.
- Windows login screen/UAC.
- Буфер обмена и передача файлов.
- Временный и постоянный доступ.
- Проверка отсутствия неожиданных внешних endpoint.

Критерий завершения: вся матрица приёмки проходит без зависимости от сторонних публичных rendezvous/relay-сервисов.

## M4 — Family Release

- Минимальный канал обновлений: клиент умеет показать, что доступна новая версия; документирована ручная процедура обновления с проверкой SHA256/подписи. Полноценное auto-update проектируется отдельным ADR после Family Release.
- **Обновление кнопкой** (идея владельца 2026-10-09). В клиенте — «Проверить обновления» / «Обновить»: та же цепочка, что `install.ps1` (последний релиз, проверка SHA256, замена файлов, перезапуск с тем же профилем), без PowerShell. **Удалённое обновление**: при подключении клиент сравнивает версию той стороны с последним релизом; если там старая — в окне сеанса «На той стороне старая версия FuntiDesk» с кнопкой «Обновить», тот компьютер сам скачивает и ставит релиз и сеанс переподключается (решение владельца 2026-10-09: без подтверждения на той стороне, чтобы не дёргать человека; помощник в сеансе управления и так может установить что угодно). Предварительно — своя нумерация сборок (сейчас у всех 1.4.9 upstream), например `1.4.9-ft.<номер сборки CI>`. Требования до реализации (ADR): источник — только релизы FuntiDesk, проверка SHA256 и подписи релиза (ключ подписи — отдельное решение, см. пункт ниже), fail closed при несовпадении; на той стороне — видимое без кнопок «FuntiDesk обновляется, сейчас переподключимся» (без скрытых действий, SECURITY.md); служба (установленный режим) обновляется так же.
- Подпись Windows-кода: выбрать сертификат, зафиксировать хранение signing key и ответственного за подпись, подписывать EXE/installer и проверить чистую Windows с Defender/SmartScreen.
- Собственная визуальная система и модель взаимодействия FuntiDesk.
- Простое первичное использование для семьи и друзей.
- Имя устройства + числовой ID.
- Избранные и недавние устройства.
- Installer и portable-дистрибутив. Portable — один самораспаковывающийся `FuntiDesk.exe` (решение владельца 2026-10-08): упаковщик upstream (`libs/portable`) переведён на идентичность FuntiDesk, распаковка в `%LOCALAPPDATA%\FuntiDesk\portable`; CI публикует его в релизе как `FuntiDesk-portable.exe` рядом с zip (сделано 2026-10-09, `build-baseline.ps1 -PortablePack`). Установка одной командой `irm https://raw.githubusercontent.com/michailr1/FuntiDesk/main/install.ps1 | iex` (сделано 2026-10-08, как в MicroRecord): файлы, скачанные PowerShell, не получают отметку «скачано из интернета», поэтому SmartScreen не останавливает даже первый запуск; скрипт проверяет SHA256 релиза. Для архива, скачанного браузером, предупреждение убирает только подпись кода с репутацией (пункт выше).
- Полный доступ без сюрпризов (решение владельца 2026-10-08). Без прав администратора портативный клиент двигает курсор, но не может нажимать в окнах администратора, окнах UAC и на экране входа (UIPI); найдено на приёмке PR #12. Продуктовый слой поверх существующего механизма повышения прав ядра: при первом запуске portable — понятное предложение «Разрешить полное управление этим компьютером?» с одним подтверждением UAC; для регулярно используемых компьютеров — понятное предложение установить службу вместо нынешней карточки про UAC.
- Безопасные настройки unattended access по умолчанию.
- Каждый передаваемый бинарный релиз связан с конкретным source tag и license notice.
- Автоматизировать цепочку release: source tag → reproducible build → SHA256 → release notes со ссылкой на Corresponding Source и license notice; допускается интеграция с основным CI.
- Собственный экран передачи файлов. Upstream-экран при узком окне разваливается (русские подписи длиннее: «Отправить» наезжает на кнопки, поле пути сжимается); найдено на проверке 2026-10-08. Передача файлов — основной сценарий, экран переделать по системе FuntiDesk. Обязательно: быстрые переходы как в «Этом компьютере» Windows — Рабочий стол, Документы, Загрузки, домашняя папка, диски (решение владельца 2026-10-08); адресная строка понимает `%APPDATA%` и другие переменные окружения.
- Терминал в продуктовом интерфейсе (решение владельца 2026-10-08): ссылка «Открыть терминал» рядом с «Посмотреть камеру» и пункт в меню устройства; разрешение `enable-terminal` на принимающей стороне включено по умолчанию; пометку «бета» снять после проверки на двух компьютерах (portable и служба, cmd и PowerShell, переподключение). Доступ агентов к командной строке клиента — отдельный ADR: консольный клиент/MCP на стороне помощника, без нового входящего API на клиенте; явное разрешение, индикатор, журнал команд.
- **Звонки вместо «Посмотреть камеру»** (решение владельца 2026-10-08, `docs/ADR-005-family-calls.md`). Семейный видеозвонок: «Позвонить» на главном экране и в меню устройства, у абонента «Входящий звонок» с «Ответить»/«Отклонить», голос включается вместе с ответом. Подключение к камере по одному паролю убрано; автоответ по паролю — настройка, по умолчанию выключена. Этап 1 — без изменения протокола (видео от абонента, голос в обе стороны); этап 2 — двустороннее видео; этап 3 — звонок без ID и пароля через семейные контакты, общий механизм с «Попросить помощи». Текстовый чат upstream — кандидат в тот же сценарий.
- Доработки звонков и главного экрана (найдено на проверке 2026-10-08): звонящему показывать «Абонент отклонил звонок»; мелодия входящего звонка; вернуть закрытую картинку главного экрана (сейчас скрытие нельзя отменить из интерфейса); при ошибке рукопожатия прямого соединения (`peer did not send SignedId`) переходить на relay, а не завершать подключение.
- **Семейный доступ** (решение владельца 2026-10-08, `docs/ADR-006-family-access.md`). Разовое сопряжение по коду из 6 цифр, дальше звонки и подключения без пароля с «Принять» на той стороне; список семьи хранится на каждом устройстве. Этап 1 — сопряжение и вход; этап 2 — «Попросить помощи» на том же механизме.
- **«Попросить помощи»** (решение владельца 2026-10-08, приоритетная собственная функция). На компьютере члена семьи — одна заметная кнопка; помощник получает уведомление «Мама просит помощи» с кнопкой «Подключиться» и подключается без диктовки ID и пароля. Требования до проектирования (нужен ADR):
  - канал уведомлений — инфраструктура FuntiDesk; сторонний мессенджер допустим только явным решением владельца, без скрытого fallback;
  - помощник заранее и явно связан с компьютером (разовое сопряжение); запрос уходит только связанным помощникам;
  - передаётся только ID и свежий одноразовый пароль с ограниченным сроком; постоянный доступ запрос не включает и не раскрывает;
  - отправитель видит, кому ушёл запрос и кто подключился, и может отменить запрос;
  - если канал недоступен — fail closed: сообщение об ошибке и обычный путь «продиктуйте ID и пароль»;
  - до мобильных клиентов помощник получает запрос в Windows-клиенте.
