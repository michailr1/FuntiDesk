# ADR-020: блокировка перебора входа статистики через CrowdSec

Статус: проект для ревью архитектора и принятия владельцем, 2026-11-11. Номер предварительный. Задание #128; дашборд — отдельный PR #130. Production-конфигурация CrowdSec/firewall не менялась.

## Что подтверждено чтением desk

- crowdsec и crowdsec-firewall-bouncer active. Установлены crowdsecurity/caddy, caddy-logs, http-logs и http-generic-bf; локальный firewall-bouncer регулярно получает decisions.
- Caddy пишет access log в существующий SSL volume. Этот файл уже включён в acquisition с type=caddy. Статистика входит в logging desk; найден существующий 401 с WWW-Authenticate Basic, соответствующий правилу auth_fail. Сырые строки, IP, учётные данные, закрытый путь и конфигурация соседних проектов не копировались в GitHub.
- Offline cscli explain на синтетическом GET/401 успешно показывает Caddy parser и auth_fail; GET/200 — Caddy parser без auth_fail. В production запросы перебора и decisions для проверки не создавались. Установленный сценарий: capacity=5, leakspeed=10s, blackhole=1m, remediation=true. Это leaky bucket, не обещание «бан ровно после шестой ошибки».
- Bouncer настроен только на INPUT. Jump в CROWDSEC_CHAIN есть в INPUT, нет в FORWARD/DOCKER-USER. Caddy находится в Docker bridge и имеет опубликованные порты. Защита опубликованного Docker HTTPS по этим данным не доказана: внешний DNAT-поток проходит FORWARD, а не INPUT.

Вывод: сбор и распознавание ошибок уже работают; просто добавить ещё один acquisition/сценарий недостаточно. Нужна проверяемая точка enforcement на пути к Caddy. Общий firewall не менять молча.

## Предлагаемый минимальный вариант

Использовать существующий firewall-bouncer и его ipsets, без плагина в Caddy, новой БД, контейнера, API-ключа или сервера. Это проще, чем заменять официальный Caddy образом с HTTP-bouncer. **Граница блокировки — опубликованный HTTPS общего Caddy, а не один URL.** Заблокированный IP потеряет доступ и к соседним HTTPS-сайтам на том же порту; это должно быть явно принято владельцем и архитектором. VPN-порты и посторонние forwarded-потоки исключаются.

Предлагаемая конфигурация для последующего небольшого реализационного PR:

1. Сохранить закрытые bouncer config, iptables/ip6tables и inspect Caddy; проверить реальный входящий интерфейс, published port и IPv4/IPv6 путь. Не выводить API-ключ и содержимое ipsets.
2. Выделить собственную цепочку FUNTIDESK_HTTPS_CS. В existing bouncer iptables_chains сохранить INPUT и добавить только эту цепочку. Блокирующими ipsets продолжает управлять сам bouncer; не привязываться к текущим именам наборов и не ссылаться извне напрямую на удаляемую им CROWDSEC_CHAIN.
3. Из DOCKER-USER направить только входящий DNAT TCP-поток опубликованного порта 443 общего Caddy в FUNTIDESK_HTTPS_CS. Матчить verified ingress interface и conntrack original destination/port, а не меняющийся IP контейнера. Прочие правила не переставлять и не очищать. Повторное применение должно проверять существование точного правила, не дублировать его.
4. Создание/восстановление цепочки и jump описать репозиторными командами и drop-in существующих units с правильным порядком Docker/bouncer; новых фоновых процессов не вводить. Проверить reboot, restart bouncer и пересоздание Caddy/Docker. При отсутствии цепи bouncer не должен уходить в restart-loop; ошибка не останавливает FuntiDesk.
5. Для IPv6 сначала установить фактический путь. Если IPv6 обслуживается host proxy, проверить INPUT; если forwarding — добавить эквивалентное ограниченное правило. До отдельного теста IPv6 защиту не заявлять. Отключать IPv6 или менять сети ради обхода задачи нельзя.

Пример ожидаемого состава настройки, **не команда поставки**:

```yaml
# В существующем конфиге bouncer, остальные поля/ключи сохраняются:
iptables_chains:
  - INPUT
  - FUNTIDESK_HTTPS_CS
```

Пока интерфейсы, transport и persistence не определены реализацией, копировать этот фрагмент в production нельзя. Вариант «просто добавить весь DOCKER-USER» отклонён: он необоснованно расширяет блокировку на другие проекты/порты.

## Приватность

Использовать текущий локальный access log; не включать log_credentials, не сохранять Basic Auth/куки/пароли/JSON-сеансы, не отправлять сырые логи в Issues/агенту. Ограничить и проверить ротацию access log; изменение общей logging-конфигурации требует отдельного scope. Закрытый путь может присутствовать в текущем серверном access log: он не является механизмом авторизации и не должен попадать в отчёты. Basic Auth остаётся обязательным независимо от CrowdSec.

Проверить текущую политику sharing CrowdSec перед передачей новых signals: никаких закрытых URL/учётных данных внешним сервисам. Новых внешних интеграций этот ADR не разрешает.

## Приёмка и откат

- Offline replay 401→auth_fail, 200→не auth_fail; уже выполнено, без бана рабочего IP.
- В изолированном тесте подтвердить путь пакета и создание/удаление точного правила. Затем контролируемый тестовый внешний IP, не адрес администратора: повторные неверные логины создают ожидаемый scenario/decision, последующий HTTPS блокируется; после удаления только тестового decision доступ возвращается.
- Верный пароль у незаблокированного адреса даёт 200; ошибочный — 401. Внешние IPv4/IPv6 тестируются отдельно. Не подменять факт packet enforcement наличием записи в cscli.
- До/после сравнить соседние сайты, VPN/SSH, другие forwarded-порты, ключи, контейнеры и их StartedAt; никаких глобальных flush/prune/restarts. Сеть и сервер DE не менять.
- Откат: удалить только помеченный FuntiDesk jump, вернуть прежний список bouncer chains/drop-in и перезапустить только bouncer. После удаления его jump очистить только собственную цепочку. INPUT и существующие decisions/ipsets не сбрасывать. Проверить восстановление HTTPS/VPN и работу CrowdSec.

Решение требуется до реализации: принять расширение защиты на весь HTTPS общего Caddy либо выбрать URL-изолированный HTTP-bouncer (новая зависимость/сборка Caddy, отдельный ADR). До этого честный статус: detection настроен, blocking Docker HTTPS не принят и не объявляется работающим.
