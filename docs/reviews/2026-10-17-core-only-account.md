# Упрощение кабинета: Core и SQLite без DE

Решение владельца от 2026-10-17: [ADR-013](../ADR-013-core-only-account.md). Инцидент с отключённым DE выявил ненужную рабочую зависимость. Она удалена, без режима обхода и без добавления новых сервисов.

## Реализация

Удалены модули API witness/recovery/relay, их CLI-команды, конфигурация независимого Compose/TLS и связанные probes/tests. Убраны зависимости reqwest и chacha20poly1305 из account; fs2 оставлен для блокировки второго процесса SQLite. API подтверждает стандартную SQLite-транзакцию на Core. В проекте Compose остаются `account` и `mail`, у API только frontend/SMTP-сети. Caddy, hbbs/hbbr и Windows-протокол не меняются.

Схема v4 удаляет служебные witness-триггеры и `recovery_state`. Аккаунты, сессии/отзывы, устройства, семья, события/ACK, избранное/история и sqlite_sequence остаются. Миграции v2/v3 и повторное открытие проверены. Исходные v2/v3 SQL оставлены только как fixtures для регрессионных проверок настоящей старой базы.

Helper обновления подготавливает проверенный CI image без запуска. При `--apply` останавливает только API, создаёт закрытую SQLite Online Backup-копию, проверяет миграцию на другой копии сравнением значений всех прикладных таблиц и integrity/foreign-key checks, затем обновляет существующий API. После готовности удаляет только старый relay проекта и его пустые сети. Ключи и остальные контейнеры сверяются; старый API не запускается на v4, старая база не восстанавливается ради отката. На DE операции не выполняются.

## Проверки

- 25 Rust-тестов, fmt и Clippy с `-D warnings` прошли. Регрессия с v3 содержит неподтверждённую recovery revision 21/confirmed 19, действующую и отозванную сессии, устройство, семью, отзыв/ACK, избранное и историю. Все прикладные значения после миграции совпали, отозванная сессия осталась недействительной.
- Настоящий Chromium с локальным API/SQLite и SMTP fixture работает без witness-процесса и переменных: вход/выход, CSRF, избранное, история/очистка, автоматическое обновление и прекращение чтений после выхода прошли.
- Helper: проверены точечная замена image, удаление только obsolete env, закрытая согласованная копия и preview без изменения исходной DB. Прежние static/browser updater tests проходят с новой версией.
- CI source `30838e7e51d1`, push run [39032123731](https://github.com/michailr1/FuntiDesk/actions/runs/39032123731) полностью прошёл, включая настоящие SMTP/configuration checks и упаковку образов. Предыдущая infra-проверка выявила оставшийся вызов удалённого CLI restore в тесте; он заменён проверкой перезапуска на той же SQLite-базе, без изменения API-кода.

## Применение

На момент записи сервер ещё на прежнем API v3 и недоступен для подтверждаемых операций. Следующий шаг — закрепить CI archive/image, проверить и применить обновление на нынешней базе Core. Не требуется пересборка Windows-клиента: API и правила доступа совместимы, синхронизация остаётся автоматической после входа. Живая приёмка двух Windows-служб остаётся отдельным пунктом.

Предварительная проверка на Core выполнена на отдельных закрытых SQLite-копиях (`core-only-preflight-20261017`): значения всех прикладных таблиц и sqlite_sequence после v4 совпали, integrity/foreign-key checks прошли. Исходная работающая DB не изменялась.

Публичный запрос, который действительно работает с базой (`auth/request` для разрешённого тестового ящика), до обновления вернул `503/service_unavailable`; это контрольная точка для повторной проверки после обновления. Почтовый код не выводился.

Обновлённый настоящий Docker SMTP smoke локально прошёл с CI static API binary: код из очереди проверился, действующая сессия сохранилась после рестарта того же API, sender/DKIM refusal и отсутствие секретов в логах подтверждены. Witness-процесс и его env отсутствуют.

Закреплена новая основная поставка `account-release.json`: CI source `30838e7e51d1`, artifact `12100049689`, ZIP SHA256 `3174e346615c11d187067241d1fa6f177b3122e95a206bc34b8e807b95e5f0cc`, Docker archive SHA256 `48450542e2075cb41c0ac82027985898c86e2bc0ba703a7cddb44d4b0913375a`. Проверены все внутренние SHA256, classic/OCI IDs и source labels. На Core обновляется только API; новые mail/server images не объявляются действующими.
