# Доступ без входа после перезагрузки (Windows, P1)

Дата: 2026-10-22. Компьютер MINIPC, служба `FuntiDesk` (LocalSystem, Automatic). Ветка `michailr1/nifty-noether-mos7q6` от `main` `6aa036d`.

**Статус: исправление в коде, на реальном Windows не проверено.** Задача не закрыта до сценариев ниже.

## Что установлено по коду

1. **Цикл службы — upstream без изменений.** `run_service`, `launch_server`, `launch_privileged_process` (`client/src/platform/windows.rs`) и `get_current_session`, `LaunchProcessWin` (`client/src/platform/windows.cc`) совпадают с RustDesk 1.5.0 (сверено diff'ом с тегом `1.5.0`). Регрессии FuntiDesk в этом месте нет; `share_rdp` по умолчанию включён, как в upstream.
2. **Служба перезапускает `--server` только в двух случаях:** сменилась выбранная сессия или процесс `--server` завершился. Живой, но недоступный `--server` (не зарегистрирован на `hbbs` или завис) служба не замечает никогда. Переподключение RDP (Event ID 25) меняет активную сессию — служба закрывает старый `--server` и запускает новый. Это ровно то, что видно на обеих загрузках: появление нового `--server` совпадает с Event 25 до секунды, и после этого доступ появляется. Значит, сам RDP не нужен — нужен перезапуск `--server`, а цикл службы делает его только по смене сессии.
3. **При отсутствии консольной сессии (`0xFFFFFFFF`) цикл пропускал и проверку живости `--server`** (`continue` в ветке тайм-аута). Умерший в это время `--server` не заменялся, пока сессия не появится.
4. **Код ошибки запуска терялся.** `LaunchProcessWin` после неудачного `CreateProcessAsUserW` вызывает `CloseHandle`, который перезаписывает `GetLastError()`; в журнал попадало «операция успешно завершена». `launch_privileged_process` при `NULL` возвращает `Ok(NULL)`; цикл повторял попытку каждые 300 мс без журнала причины.
5. **«В сети» означает, что регистрация была меньше 30 с назад** (`server/src/rendezvous_server.rs`, `handle_online_request`, `REG_TIMEOUT`). Если до входа узел действительно показывался «в сети», `--server` работал и был зарегистрирован, а тайм-аут возник позже: запрос не дошёл до `--server` или не был обработан. Различить эти случаи прежние журналы не позволяют — добавлен журнал полученных `PunchHole`/`RequestRelay`.

**Не установлено:** почему `--server`, запущенный при загрузке, недоступен. Кандидаты: запуск через ~10 с после загрузки, до готовности сети/DNS; зависание; отображение «в сети» в другой момент, чем попытка подключения. Ответ — в журналах (см. «Что собрать»).

**Несоответствие в данных:** у PID 8208 указано только TCP `→ 173.249.195.36:443`. Порт 443 — личный кабинет (`docs/NETWORK_ALLOWLIST.md`); сигнализация идёт по TCP 21116 (ADR-004). У работающего `--server` должно быть соединение на `:21116`; проверить полным `Get-NetTCPConnection -OwningProcess <pid>`.

## Исправление (коммит на ветке)

- `client/src/platform/windows/funti_service.rs` (новый): журнал каждого запуска `--server` (причина, выбранная сессия, консольная и активная сессии, доступные сессии, PID, ошибка; повторные неудачи — первая и затем раз в ~30 с); журнал выхода `--server` с кодом; раз в 60 с служба спрашивает `--server` по IPC (`OnlineStatus`) о регистрации и пишет переходы; **если `--server` 5 минут не зарегистрирован (или не отвечает по IPC) и у него нет видеосеансов — служба закрывает его, при необходимости завершает и запускает новый** в текущей сессии. Второй `--server` рядом не запускается: новый стартует только после выхода старого.
- `run_service`: тонкие вызовы; при `0xFFFFFFFF` пропускается только смена сессии, проверка живости работает. В сессию `0xFFFFFFFF` запуск не выполняется (работающий `--server` не закрывается).
- `LaunchProcessWin`: сохраняет код ошибки `CreateProcessAsUserW`.
- `rendezvous_mediator.rs`: журнал полученных `PunchHole`/`RequestRelay` (не чаще раза в 10 с, только адрес сервера).

Модель безопасности не менялась: `--server` по-прежнему SYSTEM с токеном `winlogon.exe` сессии, IPC — прежняя авторизация главного канала (служба — SYSTEM). Авторизация подключений, пароли, Windows Hello, NLA, UAC не затронуты. Журналы без секретов: номера сессий и процессов, коды ошибок, состояния.

Затронутые пути: только служба Windows (`--service`) и приём запросов в `rendezvous_mediator` (одна строка журнала). Передача файлов, буфер обмена, relay не менялись.

## Журналы

- Служба: `C:\Windows\ServiceProfiles\LocalService\AppData\Roaming\FuntiDesk\log\service\`
- `--server`: `C:\Windows\ServiceProfiles\LocalService\AppData\Roaming\FuntiDesk\log\server\`

Пишутся до входа пользователя, читаются через RDP администратора. Строки службы начинаются с `FuntiDesk service:`.

### Что собрать до установки (с текущей сборки)

Журналы прошлых загрузок уже лежат в этих папках и, вероятно, содержат ответ. До установки новой сборки скопировать обе папки (в архив вне репозитория, не коммитить: там ID и адреса). Искать: `session id`, `session changed`, `Failed to launch privileged process`, `start --server`, `start tcp`, `rendezvous mediator error`, `keep_alive` (успешная регистрация) — по времени 14:31–16:28 и 17:14–17:41.

## Сборка

Windows-сборка: workflow `R21 Windows clean build` (`workflow_dispatch`, без публикации релиза), артефакт `funtidesk-windows-x64-<sha>`. Релиз не выпускался.

## Установка на MINIPC (вручную, через RDP `minipc\admin`)

1. Убедиться, что RDP-доступ `minipc\admin` работает. Не завершать RDP-сеанс, не перезагружать без готовности.
2. Резервная копия: `Copy-Item 'C:\Program Files\FuntiDesk' 'C:\FuntiDesk-backup-<дата>' -Recurse` и запись `& 'C:\Program Files\FuntiDesk\FuntiDesk.exe' --version`.
3. Скопировать журналы (выше).
4. `sc stop FuntiDesk`; дождаться остановки; закрыть FuntiDesk в сеансе (трей).
5. Скопировать содержимое артефакта поверх `C:\Program Files\FuntiDesk`.
6. `sc start FuntiDesk`; проверить в журнале службы строку `FuntiDesk service: --server started, pid …`.

## Откат

`sc stop FuntiDesk` → `Remove-Item 'C:\Program Files\FuntiDesk' -Recurse` → `Copy-Item 'C:\FuntiDesk-backup-<дата>' 'C:\Program Files\FuntiDesk' -Recurse` → `sc start FuntiDesk` → `--version` совпадает с записанной. Конфигурация (ID, ключи, семья) хранится в профиле SYSTEM и при замене папки не меняется.

## Известные ограничения

- Перезапуск по отсутствию регистрации срабатывает через 5–6 минут; при долгом отсутствии сети `--server` перезапускается раз в ~6 минут (без сеансов — без последствий).
- Сеансы передачи файлов без видео не считаются: при 5 минутах без регистрации такой сеанс может быть прерван.
- Если первопричина — сеть до входа пользователя (например, профиль Wi-Fi только для пользователя), перезапуск не поможет; журнал покажет `start tcp` с ошибками до входа.
