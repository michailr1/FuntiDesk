# Личный кабинет в браузере: локальная проверка

Дата: 2026-10-13. **Это проверка реализации в локальной среде, не end-to-end приёмка на реальных компьютерах или внешней почте.** Production, Caddy, DNS и внешние почтовые ящики не изменялись.

## Источник и результат

База API-ветки: `bf15eb592b84a5cd7d7ad7ed6474fea4e1021cb5`. Сайт перенесён только из `web/artifact/` [commit `0344118bcc88a6185b81f701ba9e43d7e8705495`](https://github.com/michailr1/FuntiDesk/tree/0344118bcc88a6185b81f701ba9e43d7e8705495/web/artifact). Все 15 исходных публичных файлов проверены по SHA-256 manifest; при read-only сравнении с `https://desk.funti.cc/` 2026-10-13 совпали все 15. Исходные hashes сохранены в `web/SOURCE.json`. Старая ветка клиента и сервера не сливалась.

Новая страница `/account/` использует только `https://desk.funti.cc/api/account/v1`: bootstrap/CSRF, почта → код, восстановление браузерной сессии, списки устройств и копий семьи, удаление по конкретному ключу, статусы доставки, выход и выход везде. Данные вставляются через `textContent`. HttpOnly-сессия не выдаётся JavaScript, bearer-токена и account-данных в storage нет. Кабинет не подключает демонстрационные скрипты и не даёт действий подключения, добавления в семью или изменения прав.

В перенесённом сайте исправлены русские имена устройств, FAQ о семейных правах/видеозвонках, ссылки Windows и Android, команда установки/portable, указание обновления кнопкой программы и порядок постоянного доступа. Добавлена ссылка на кабинет. У сайта один источник и воспроизводимый публичный архив.

## Проверки

- `node --check` прошёл для всех JS сайта, кабинета и браузерного теста.
- `scripts/web/package.py` сверяет manifest с 18 публичными файлами. Две упаковки одинаковых байтов дали одинаковый SHA-256. README, SOURCE, manifest и тестовые серверы в публичный архив не входят.
- Статические ссылки кабинета разрешаются в существующие файлы. В исходной демонстрации выявлена унаследованная ссылка на отсутствующий `/assets/iphone-home.png`; её публичный URL вернул HTTP 404. Она не относится к кабинету и отмечена отдельно.
- Настоящий Chromium со страницей кабинета прошёл сценарии против локального account binary: неверный код, ограничение отправки, повторная отправка, вход и восстановление cookie после reload. Cookie проверена как Secure/HttpOnly/SameSite=Strict; web-storage остался пустым.
- Имя семейного устройства с HTML-разметкой осталось буквальным текстом: изображение и обработчик события не создавались.
- Ответ первого `/family/remove` намеренно потерян после обработки настоящим API. Повтор отправил тот же случайный 256-битный `request_id`; в базе остался один event и две доставки.
- Подписанные подтверждения тестовых устройств изменили статус с 0/2 на 1/2, затем 2/2. Проверен текст частичного журнала при `has_more=true`; UI не объявляет полную доставку по обрезанному массиву.
- `/logout-all` отозвал также предварительно созданную native-сессию; кабинет очистил показанные данные. Проверен обычный выход и недоступный bootstrap с последующим повтором.
- Smoke перенесённого сайта прошёл в Chromium при ширине 1440 и 375 px, без ошибок JS и горизонтального выхода за экран.
- Кабинет проверен визуально на desktop и при ширине 375 px; горизонтального выхода за экран нет. Ошибок JavaScript в браузерных сценариях нет.

Браузерная проверка воспроизводится `node scripts/web/account-browser-test.mjs` после сборки account binary и установки инструментов разработки, описанных в `web/README.md`. SMTP-приёмник и реестр используют только loopback/локальный Unix socket. Письма адресам `.invalid` остаются в памяти; секрет и SQLite создаются вне репозитория и удаляются после проверки. Для проверки повторной отправки между минутными окнами очищаются минутные лимиты только тестовой базы.

## Границы и регрессионная поверхность

Изменены только новый `web/`, упаковка/локальные проверки в `scripts/web/` и этот отчёт. Клиент, сервер, account API и VPN-конфигурация не менялись. Из существующего web-исходника изменены только тексты/ссылки, расположение постоянного доступа, навигация к кабинету и стиль команды установки; остальная демонстрационная логика сохранена.

Рабочий запуск ещё требует account/SMTP/DKIM-инфраструктуру, согласованный Caddy-патч и DNS, безопасные HTTP-заголовки страницы, доставку во входящие и проверку реальных Windows-служб. Тестовый реестр не доказывает интеграцию с production hbbs; тестовый ack не доказывает применение удаления локальной семьёй. Редиректы и токены в браузерном API не используются, но реальные TLS/Caddy и framing-заголовки должны проверяться после согласованного размещения.

Публичный mobile-демо-исходник содержит отсутствующую картинку телефона. Изменения демонстрационных настроек, уведомления обновления и полного соответствия текущему UI выходят за реализацию кабинета и остаются отдельной работой. Merge, push/PR, deploy и внешние сообщения этой проверкой не выполнялись.


## Повторная проверка с независимым состоянием — 2026-10-14

Браузерный fixture теперь явно запускает `witness-init`, отдельный witness и `initialize` перед API. На статическом API binary из commit `ffd270b85e8e6761c0a54219c6e3d2fce70b50e1` повторно прошёл полный сценарий Chromium: вход, неверный/повторный код и лимит, HttpOnly cookie после reload, XSS-текст, отсутствие web storage, повтор удаления с прежним request_id после потерянного ответа, доставка/ACK/неполный список, выход/выход всех сессий и retry после недоступности API. Backend при этом подтверждает изменения в зашифрованном независимом состоянии; fixture не отключает эту проверку. Это локальная инженерная проверка, не реальная доставка внешней почты и не Windows-приёмка.
