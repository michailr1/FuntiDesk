## Как работать с этим документом

1. Каждое задание имеет ID `R-xx`, приоритет и критерии приёмки. Заведите их в Linear (одно задание — одна задача или подзадача) со ссылкой на этот документ.
2. Если вы не согласны с заданием или меняете решение, запишите в разделе «Ответ разработчика» в конце документа, что именно и почему. Молча пропускать задание нельзя.
3. По каждому закрытому заданию укажите в ответе: commit SHA, доказательства (вывод команды, лог, скриншот) и статус.
4. Одно свойство безопасности — один коммит. Не смешивать security-правки с брендингом и UI.
5. Каждое расхождение с upstream в коде помечается комментарием `// FUNTIDESK: <причина>` (в shell/yaml — `# FUNTIDESK:`).

Приоритеты:

- **P0** — исправить сейчас, до любой работы над M2.
- **P1** — обязательная часть M2; без этого сборку нельзя передавать людям.

- **P3** — внести в план M3/M4.

## Общая оценка

Идея, порядок этапов и дисциплина хорошие: ADR до кода, импорт с сохранением истории, неизменённая baseline-сборка до патчей, образ сервера закреплён по digest, минимальный набор портов. Замечания ниже не отменяют выбранное направление, они закрывают конкретные дыры.

Главные находки:

1. `hbbr` сейчас работает как открытый relay (R-01).
2. Клиент upstream при ошибке проверки ключа сервера **продолжает соединение без шифрования**. Этого нет в карте P1–P6 из `docs/UPSTREAM_REVIEW.md`, и без исправления требование fail closed не выполняется (R-10).
3. Кроме `custom.txt`, есть ещё несколько каналов, через которые клиент можно перенаправить на чужой сервер: имя exe-файла, опции конфига и fallback в `get_key()` (R-11, R-12).

## P0 — сервер (M1-хвосты)

### R-01. Включить проверку ключа на `hbbr`

**Факт.** `infra/funtidesk-server/compose.yaml`: `command: ["hbbr"]` без `-k`. В `server/src/hbbr.rs:39-42` ключ берётся из `-k` или env `KEY`, по умолчанию пустой. В `server/src/relay_server.rs:430` пустой ключ отключает проверку. Итог: любой RustDesk-клиент может использовать наш VPS как бесплатный relay.

У `hbbs` ключ по умолчанию `-` (`server/src/main.rs:35`), проверка там включена. Но это неявное поведение.

**Сделать.**

- `hbbr`: `command: ["hbbr", "-k", "_"]`.
- `hbbs`: явно `command: ["hbbs", "-r", "${FUNTIDESK_FQDN}:21117", "-k", "_"]`, чтобы не зависеть от default.
- Добавить `depends_on: [hbbs]` для `hbbr`. `gen_sk(300)` в `hbbr` ждёт появления `id_ed25519` всего **300 мс** (`server/src/common.rs:107-111`), после чего генерирует собственную пару. На существующем сервере ключ уже есть, но на чистом восстановлении возможна гонка.
- `verify.sh`: проверить, что строка `Key: <pk>` в `docker logs funtidesk-hbbs` и `docker logs funtidesk-hbbr` совпадает с содержимым `id_ed25519.pub`. При расхождении — ошибка.
- Передеплоить на `desk.funti.cc`.

**Приёмка.**

- `verify.sh` на сервере выводит `SERVER_VERIFY_OK=true` с новой проверкой ключа обоих сервисов.
- Публичный ключ не изменился после передеплоя (сравнить с записанным до изменения).
- В `docs/SERVER_DEPLOYMENT.md` отражено, что оба сервиса работают с `-k _`.

### R-02. Записать фактическую приёмку M1

**Факт.** Commit `31c58fa` утверждает, что live-acceptance принята, но в репозитории нет ни публичного ключа сервера, ни вывода `verify.sh`, ни развёрнутого commit. Для Windows такой раздел есть (`docs/WINDOWS_BASELINE_BUILD.md`), для сервера — нет. Публичный ключ нужен для M2 и секретом не является.

**Сделать.**

- В `docs/SERVER_DEPLOYMENT.md` добавить раздел «Фактическая приёмка»: дата, развёрнутый commit, image digest, `PUBLIC_KEY`, вывод `verify.sh`, результат `restore-check.sh`, подтверждение off-host копии (где хранится, без секретов), проверка внешней доступности портов (с какого хоста).
- `deploy.sh`: печатать `git -C "$REPO_DIR" rev-parse HEAD` и записывать его в `/opt/funtidesk/DEPLOYED_COMMIT`. Если в `$REPO_DIR` есть незакоммиченные изменения — ошибка (production должен быть воспроизводим из репозитория, правило 8 `AGENTS.md`).

**Приёмка.** Раздел заполнен реальными данными. Повторный `deploy.sh` на грязном дереве завершается ошибкой.

### R-03. Backup: шифрование и настоящий restore-check

**Факт.**

- `scripts/server/backup.sh` создаёт незашифрованный `tar.gz` с приватным ключом. По документации его нужно уносить off-host, то есть приватный ключ сервера окажется вне VM в открытом виде.
- `scripts/server/restore-check.sh` проверяет только, что файлы непустые. Он не проверяет `.sha256` и не проверяет, что пара ключей согласована.

**Сделать.**

- Шифровать архив перед выходом с хоста (`age` с публичным ключом получателя, принадлежащим владельцу; публичный ключ получателя можно хранить в репозитории, приватный — только у владельца). Либо `gpg` — на выбор архитектора, решение записать.
- `restore-check.sh`:
  - проверять `sha256sum -c` по файлу `.sha256`;
  - декодировать `id_ed25519` (base64, 64 байта) и `id_ed25519.pub` (base64, 32 байта) и проверять, что последние 32 байта приватного ключа равны публичному. Формат — `server/src/common.rs:107-147`;
  - опционально сравнивать с ожидаемым публичным ключом из `docs/SERVER_DEPLOYMENT.md` (R-02).
- Описать процедуру восстановления на чистой VM шаг за шагом, а не только проверку архива.

**Приёмка.**

- Архив с изменённым байтом отклоняется.
- Архив, где `.pub` не соответствует приватному ключу, отклоняется.
- Проведено одно реальное восстановление на временной VM или в контейнере: сервер поднялся с тем же `PUBLIC_KEY`. Результат записан.

### R-04. Мелкие правки серверных скриптов

- `apply-firewall.sh`: порт SSH не хардкодить. Определять из `sshd -T | awk '/^port /{print $2}'` или требовать переменную `SSH_PORT`. Отказываться работать, если SSH-порт не определён.
- `verify.sh` не должен менять состояние. `chmod` перенести в `deploy.sh`, а в `verify.sh` только проверять права (`600` на `id_ed25519`) и падать при несоответствии.
- `verify.sh`: сверять `docker port funtidesk-hbbs` / `funtidesk-hbbr` со списком разрешённых портов. Опубликованные Docker-порты обходят UFW, поэтому firewall не является гарантией «только минимальные порты». Это ограничение записать в `docs/SERVER_DEPLOYMENT.md`.
- Прогнать все `scripts/server/*.sh` через `shellcheck`, исправить предупреждения.

**Приёмка.** `shellcheck` чистый; `verify.sh` запускается дважды подряд без изменения файлов; при добавлении лишнего порта в compose `verify.sh` падает.

## P1 — security-периметр клиента (обязательная часть M2)

Все задания этого раздела — **блокер передачи любой сборки людям**. Для каждого нужен автоматический тест там, где это возможно (`client/libs/hbb_common` — unit tests), и ручной сценарий в security acceptance.

### R-10. Fail closed в handshake — главная находка

**Факт.** `client/src/client.rs:759-792`, `secure_connection()`: если `signed_id_pk` пуст или подпись от rendezvous не проходит проверку ключом сервера, клиент пишет `Handshake failed` в лог и **продолжает соединение без шифрования** (`conn.send(&Message::new())` и `return Ok(option_pk)`).

На принимающей стороне `client/src/server.rs:206-240`, `create_tcp_connection()`: при `secure == false` или пустом `asymmetric_value` сессия тоже идёт без шифрования.

Это прямо противоречит `docs/SECURITY.md` («неправильный/неизвестный server key приводит к отказу»). Этой точки нет в таблице P1–P6 `docs/UPSTREAM_REVIEW.md`.

**Сделать.**

- Подключающаяся сторона: любой случай, когда подписанный ключ пира отсутствует, не проверяется ключом сервера FuntiDesk или `id` не совпадает, — возвращать ошибку и не продолжать соединение. Пользователю показывать понятное сообщение («Не удалось проверить подлинность устройства»), а не молча подключаться.
- Принимающая сторона: не принимать сессию без установленного шифрования. Проверить все пути: `secure == false`, пустой `asymmetric_value`, некорректный `PublicKey`.
- Проверить пути, где signed pk не приходит вообще: прямое подключение по IP (`direct-server`), LAN discovery, relay. Для production они либо проходят проверку, либо отключены (см. R-15).

**Приёмка.**

- Тест: `hbbs` с **другим** ключом (поддельный rendezvous) — соединение отклоняется на обеих сторонах, незашифрованной сессии нет.
- Тест: клиент с неверным `key` — отказ.
- Тест: принимающая сторона получает пустой `PublicKey` — отказ.
- В ответе разработчика перечислены все найденные пути установления сессии и чем закрыт каждый.

### R-11. Убрать конфигурацию через имя exe-файла

**Факт.** `client/src/platform/windows.rs:2126` `get_license_from_exe_name()` извлекает хост и ключ из имени exe. Результат:

- попадает в `EXE_RENDEZVOUS_SERVER` (`windows.rs:2165`), которая имеет наивысший приоритет в `Config::get_rendezvous_server()` (`client/libs/hbb_common/src/config.rs:913-934`);
- **сохраняется в конфиг** через `Config::set_option("key")` и `("custom-rendezvous-server")` (`windows.rs:1675-1676`), то есть переименованный бинарник перенаправляет клиент навсегда;
- возвращается из `get_key()` раньше всего остального (`client/src/common.rs:1804-1810`).

**Сделать.** В production-сборке этот канал полностью отключить во всех трёх местах. Не парсить имя файла для инфраструктурных параметров.

**Приёмка.** Exe, переименованный в `FuntiDesk-host=evil.example,key=AAAA....exe`, продолжает работать только с `desk.funti.cc` и нашим ключом; конфиг пользователя не изменён.

### R-12. Жёсткая привязка к инфраструктуре FuntiDesk без fallback

**Факт.**

- `config.rs:120-121`: `RENDEZVOUS_SERVERS = ["rs-ny.rustdesk.com"]`, `RS_PUB_KEY` — upstream.
- `config.rs:913-960`: выбор rendezvous из пяти источников, включая пользовательскую опцию `custom-rendezvous-server`, сохранённый конфиг и `rendezvous-servers`.
- `common.rs:1820-1822`: `get_key()` при пустом ключе подставляет `RS_PUB_KEY`. `client.rs:765-769`: то же в `secure_connection()`.
- Дополнительные опции, влияющие на инфраструктуру: `relay-server`, `api-server`, `key`, `rendezvous-servers` (`config.rs:2936`, `2954` и далее).

**Сделать.**

- Задать FuntiDesk endpoint и публичный ключ сервера (из R-02) как значения, зафиксированные при сборке.
- В production `get_rendezvous_server(s)`, relay, api и `key` возвращают только значения FuntiDesk. Пользовательские опции и сохранённый конфиг для этих параметров игнорируются.
- Пустой или некорректный встроенный ключ — ошибка запуска/подключения, а не подстановка другого ключа.
- В клиентском дереве не должно остаться `rs-ny.rustdesk.com` и `OeVuKk5nlHiXp+APNn0Y3pC1Iwpwn44JGqrQCsWqmBw=` (кроме тестов, которые проверяют их отсутствие). Серверную копию `hbb_common` не трогать.
- Предпочтительный механизм — `HARD_SETTINGS` / `BUILTIN_SETTINGS` / `OVERWRITE_SETTINGS` (`config.rs:76-83`) плюс минимальные правки функций выбора. Выбор механизма записать.

**Приёмка.**

- Unit tests в `client/libs/hbb_common`: при любом содержимом конфига и опций функции выбора возвращают только значения FuntiDesk.
- Ручной тест: в `%APPDATA%\...\config\*.toml` вписан чужой сервер и ключ — клиент их игнорирует.
- Проверка по сети (R-14): при недоступном `desk.funti.cc` клиент не обращается ни к одному upstream-хосту.

### R-13. Отключить custom client (ADR-002)

Реализовать ADR-002 как есть: `read_custom_client()` (`client/src/common.rs:2181`) и `read_custom_client_advanced_settings()` (`common.rs:2105`) в production не вызываются и не применяют ничего.

**Приёмка.** Тесты из ADR-002: отсутствие `custom.txt` ничего не меняет; `custom.txt`, подписанный upstream-ключом, не меняет `app-name`, endpoints и policy.

### R-14. Аудит внешних обращений

**Факт.** Известные внешние обращения: `https://api.rustdesk.com/version/latest` (update check, `common.rs:952`), `https://admin.rustdesk.com` как api-server по умолчанию (`common.rs:1083`), ссылки на rustdesk.com в `src/client.rs` и `src/lang/*`.

**Сделать.**

- Отключить update check и api-server по умолчанию (или заменить на наши, если функция нужна).
- Провести сетевой аудит собранного клиента: чистая Windows VM, запись DNS и TCP/UDP (например, Wireshark или Sysmon), сценарии «запуск», «подключение», «сервер недоступен», «неверный ключ».
- Результат записать в `docs/SECURITY.md` как явный список разрешённых endpoint.

**Приёмка.** В записях аудита нет обращений к хостам вне списка. Список закоммичен.

### R-15. Безопасные настройки доступа по умолчанию

Через встроенные настройки (см. R-12) задать и зафиксировать для production:

- `direct-server` (прямой доступ по IP) — выключен и не включается пользователем, пока для него не решён R-10;
- `enable-lan-discovery` — выключено;
- `allow-remote-config-modification` — выключено;
- постоянный пароль (unattended) — выключен по умолчанию, включается только явно владельцем устройства;
- временный пароль — включён, виден как временный;
- `approve-mode` / `verification-method` — выбрать и записать осознанно.

Константы опций — `client/libs/hbb_common/src/config.rs:2915-2954`.

**Приёмка.** Таблица «опция → значение → можно ли менять пользователю» в `docs/SECURITY.md`. Ручная проверка на чистой установке.

**Факт.** В корне репозитория нет `.github/workflows`. Workflows внутри `client/.github` и `server/.github` GitHub не запускает.

**Сделать** (`.github/workflows/ci.yml`):

- `shellcheck scripts/**/*.sh`;
- `docker compose -f infra/funtidesk-server/compose.yaml config` с `.env.example`;
- `cargo test` для `client/libs/hbb_common` (сюда же тесты R-12);

- проверка на секреты (например, gitleaks) по диффу.

Сборку Windows в CI можно отложить, но решение записать.

**Приёмка.** CI зелёный на `main`; ветка с намеренно возвращённым upstream-ключом падает.

### R-21. Закрепить внешние бинарные зависимости сборки

**Факт.**

- `scripts/windows/build-baseline.ps1:97` скачивает `https://github.com/rustdesk/engine/releases/download/main/windows-x64-release.zip` — плавающий тег `main` без проверки хэша. Это нативный Flutter engine, который попадает в наш бинарник: риск подмены и невоспроизводимость.
- `scripts/windows/bootstrap.ps1:50` скачивает LLVM installer без проверки хэша.
- Flutter клонируется по тегу без проверки commit.

**Сделать.**

- Скачивать engine по конкретному неизменяемому URL/asset и проверять SHA256, записанный в скрипте. Если upstream не даёт неизменяемого asset — зеркалировать проверенный архив в наш release и записать его происхождение.
- SHA256 для LLVM installer.
- После clone Flutter проверять `git rev-parse HEAD` против ожидаемого commit.
- Все хэши записать в `docs/WINDOWS_BASELINE_BUILD.md`.

**Приёмка.** Скрипт падает при несовпадении хэша любой скачанной зависимости. Сборка проходит заново на чистой машине.

### R-22. Привести документацию в соответствие

- `docs/ARCHITECTURE.md`, «Открытые решения M0»: убрать уже решённые пункты (структура импорта — ADR-001), оставить реально открытые.
- `docs/SECURITY.md`: явно записать, что ключ сервера — **публичный**, он защищает клиента от подмены сервера, но не ограничивает, кто может пользоваться сервером. Контроль доступа к устройствам — пароли и approve-mode.
- `docs/SERVER_DEPLOYMENT.md`: ограничение «Docker обходит UFW» (R-04).
- Сократить дублирование между `docs/UPSTREAM.md`, `docs/UPSTREAM_REVIEW.md` и ADR-001: в одном месте факты, в остальных — ссылки.
- Явно записать, что сервер разворачивается из upstream-образа `ghcr.io/rustdesk/rustdesk-server`, а дерево `/server` сейчас в production-сборке не используется. Указать, когда и зачем мы перейдём на собственную сборку сервера (если перейдём).

## P3 — внести в план

### R-30. Канал обновлений до Family Release

Update check upstream будет отключён (R-14), а своё обновление в `docs/ROADMAP.md` стоит в разделе «Дальше». Инструмент удалённого доступа без обновлений у родственников — риск безопасности.

### R-31. Подпись кода Windows

### R-32. Обновления сервера и мониторинг

- Политика обновления `hbbs`/`hbbr`: как отслеживаются security-релизы `rustdesk-server`, кто и как обновляет digest, как откатываться.
- Простой внешний мониторинг доступности портов 21115–21117 с уведомлением владельца.
- Оценить трафик relay на текущем VPS (лимиты канала и трафика тарифа).
