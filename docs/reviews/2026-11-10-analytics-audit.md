## Этап 1: фактические источники

| Метрика | Источник без нового клиента | Точность / ограничения |
|---|---|---|
| Аккаунты | `accounts`, отдельно disabled=0 | Текущие строки, не люди и не все когда-либо созданные |
| Устройства кабинета | `devices.pk`, UNIQUE | Только привязанные; переустановка/копия ключа и удаление меняют смысл |
| Регистрации hbbs | `peer.id`, отдельно DISTINCT непустой pk | Не установки и не люди; остаточные регистрации сохраняются |
| Активность 1/7/30 дней | `devices.last_seen` | Только кабинет; bind/family/ACK обновляют время; глобальная DAU недоступна |
| Активные аккаунты | DISTINCT account_id у активных устройств | Прокси активности аккаунта, не число людей |
| Успешные подключения | `connection_history` | Неполные клиентские сообщения + импорт истории, 90 дней/1000 на аккаунт/очистка |
| Попытки и успешность | Полного источника нет | hbbs запрос не означает успешный handshake; знаменателя нет |
| P2P / relay | hbbr пишет pairing/close | Pairing не доказывает успешную авторизацию; P2P исход не наблюдается сервером |
| Версии | `devices.version` | Только кабинет, клиентские данные; hbbs version в запросах не сохраняется как реестр |
| Платформы / качество | Нет подходящего постоянного источника | Не угадывать по IP, версии, имени или скачанному asset |
| Скачивания | GitHub Releases assets download_count | Повторные скачивания, checksums и серверные файлы; не установки |

`peer.last_reg_time` — Instant в памяти, после рестарта теряется. В SQLite `peer` есть created_at, но нет last_seen. `PeerInfo` хранит IP, не версию/платформу. Глобальную активность из регистрации вывести нельзя. Логи содержат ID/IP и pairing UUID: их нельзя копировать в публичные Issues или использовать как готовую продуктовую аналитику. Переход на DEBUG ради аналитики не предлагается.

Actions: server-monitor каждые 10 минут проверяет TCP 21115–21117 и HTTPS, открывает/закрывает outage issue; не проверяет успешное защищённое соединение и UDP heartbeat. Account/browser/server/client CI проверяют сборки и сценарии, не аудиторию. Наличие workflow не доказывает его успешные последние запуски.

## Этап 2: MVP и безопасный запуск

Подготовлен [проект ADR-019](../ADR-019-minimal-analytics.md). CLI читает только переданные согласованные копии и формирует локальный HTML 0600; нет нового endpoint, процесса, БД, контейнера, миграции или клиентского события. В отчёте доступны дневные ряды оставшихся аккаунтов/истории, активность кабинета и версии; качество и глобальная аудитория отмечены недоступными.

На доверенном хосте с уже предоставленным владельцем доступом сначала определить deployed commit/image и фактический путь DB по действующей документации, **не выводя env/secrets**. Снять закрытую согласованную SQLite-копию через штатный backup; для WAL нельзя копировать один основной файл. Вариант ручного read-only backup при доступном sqlite3:

```bash
umask 077
sqlite3 -readonly /verified/path/account.sqlite '.timeout 1000' '.backup /private/account-copy.sqlite'
sqlite3 -readonly /verified/path/db_v2.sqlite3 '.timeout 1000' '.backup /private/hbbs-copy.sqlite'
python3 scripts/analytics/snapshot.py --account-copy /private/account-copy.sqlite --hbbs-copy /private/hbbs-copy.sqlite --html /private/analytics.html
python3 scripts/analytics/test_snapshot.py
```

Пути-примеры заменить проверенными; копии и HTML держать вне webroot, не передавать в GitHub. Запуск только после ревью PR; production здесь не менялся. При блокировке/ошибке не перезапускать API, а повторить диагностику согласованно. Удалить временные копии после чтения, отчёт через семь дней. Время копирования каждого источника записать отдельно: CLI observed_at — время вычисления, а не свежесть источника.

Проверено локально: пять тестов, настоящие SQL-схемы v4/v5, read-only и неизменность файла, границы 1/7/30 дней, исключение будущего last_seen, дедупликация ключей, фильтрация произвольной версии, отсутствие персональных строк, закрытые права и отказ перезаписи. HTML проверен в системном Chromium через Playwright set_content: заголовок, null и отсутствие page errors; открытие file:// запрещено политикой этой cloud-среды и не принято как проверенное. Нулевые таблицы отличаются от отсутствующего источника (null). Ограничение: нет production-выборки и E2E, нет непрерывного сбора или готового авторизованного веб-дашборда.
