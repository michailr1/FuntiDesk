# Автоматическое обновление HTTPS-сертификата независимой копии

Владелец разрешил эту настройку 2026-10-14. Это отдельная операция с TLS на DE; запуск account/SMTP, изменение DNS и приёмка кабинета остаются следующими шагами.

## Источник и доступ к ключу

Перед установкой проверить, что системный Caddy на DE автоматически получает и продлевает сертификат `de.funti.cc`. По метаданным его хранилища выбрать точные `.crt` и `.key` этого домена. Пути не угадывают; приватный ключ в вывод и в репозиторий не попадает. Если сертификат обновляется вручную, одной синхронизации недостаточно: сначала нужен действующий механизм выпуска и продления.

Системный Caddy продолжает управлять ACME. Новый почасовой таймер передаёт проверенную пару в `/opt/funtidesk-account-witness/secrets/tls`. Исходное хранилище Caddy не монтируется в Docker. Каталог получателя — root/`0700`, файлы — root/`0600`; witness и account не получают TLS-ключ. В журналы записывается только результат операции, без PEM и ответов подпроцессов.

До публикации проверяются доверенная цепочка, имя `de.funti.cc`, срок не менее суток и совпадение открытого ключа. Незащищённый ключ, неправильная пара или ошибка проверки сохраняют прежний сертификат. Проверяются уже скопированные файлы: асинхронная замена источника не может пройти проверку с несовпадающей парой.

Новая пара и каталог синхронизируются с диском, затем атомарно заменяется ссылка `current`. Имена `fullchain.pem` и `privkey.pem` ведут через неё. После успешной смены сохраняются текущая и предыдущая генерации. При ошибке `fsync` после смены ссылки восстанавливается прежняя цель; неполный откат не удаляет потенциально используемое поколение.

## Перезагрузка собственного Caddy

Compose-проект независимого сервиса запускают с явным именем `funtidesk-account-witness`. CLI скрипта закреплён за этим проектом. Он выбирает только его работающий service `caddy` по Docker labels; host/shared-container network namespaces не подходят. Admin endpoint собственного контейнера слушает **только `127.0.0.1:2019` внутри контейнера**, порт не публикуется. Системный Caddy DE и остальные сайты не перезагружаются.

`caddy reload --force` нужен даже при одинаковом JSON: меняются файлы сертификата. Он выполняется почасово и при совпадающих файлах, чтобы завершить обновление после обрыва процесса между публикацией и reload. При ошибке reload во время смены пары ссылка возвращается к предыдущей генерации, операция завершается отказом. При отсутствии работающего собственного Caddy готовятся только файлы; следующий запуск читает актуальную пару. Уже работающий Caddy с прежним `admin off` сначала требует однократного перехода на новый конфиг.

## Установка на DE

Из проверенного чистого checkout закреплённого commit, после проверки источника:

```sh
bash scripts/account/install-witness-tls.sh \
  /точный/путь/de.funti.cc.crt /точный/путь/de.funti.cc.key
```

Команда требует root. Источники в `/root`, `/home`, `/run/user` отвергаются до установки, поскольку unit закрывает домашние каталоги через `ProtectHome=true`. Она отказывается заменять конфигурацию без собственного маркера, проверяет пути, устанавливает скрипт, закрытый файл путей, systemd service/timer и выполняет первую синхронизацию. Существующие обычные TLS-файлы получателя требуют явной миграции; скрипт не удаляет их автоматически.

Контроль без чтения приватного ключа:

```sh
systemctl is-active funtidesk-account-witness-tls.timer
systemctl show funtidesk-account-witness-tls.service -p Result -p ExecMainStatus
systemctl list-timers funtidesk-account-witness-tls.timer
openssl x509 -in /opt/funtidesk-account-witness/secrets/tls/fullchain.pem \
  -noout -dates -checkhost de.funti.cc
```

Ошибка service требует проверки источника и собственного Caddy; проверку TLS не отключают. После запуска endpoint проверяют доверие/имя через HTTPS на 8447 и свежий подписанный witness head. Файловая синхронизация сама по себе не означает работоспособность всего кабинета.

## Проверки

`test-witness-tls.py` проверяет отказ неверному имени/паре/правам, откат при ошибке reload, сбой `fsync` после смены ссылки и при откате, повтор и права файлов. `smoke-witness-tls.py` использует тестовый CA, настоящий Caddy и закрытый witness, прерывает обновление после публикации, затем повторяет его с теми же файлами и сверяет новый сертификат реального TLS-соединения. Подписанный канал, отказ HMAC и постороннему пути проверяются в том же сценарии. Тестовые ключи, контейнеры и сети удаляются.
