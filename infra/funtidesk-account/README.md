# Поставка кабинета: проект конфигурации

Статус: конфигурация поставки кабинета. Основной запуск разрешён владельцем; приватные сервисы уже включены, публичное переключение и E2E-приёмка ещё не завершены. Актуальное состояние — [отчёт продолжения](../../docs/reviews/2026-10-15-account-deploy-continuation.md), действующие команды — [ACCOUNT_DEPLOYMENT.md](../../docs/ACCOUNT_DEPLOYMENT.md). Следующие сведения о сервере описывают историческую проверку до запуска.

## Проверенный текущий сервер

2026-10-13 агент Windows миниПК через подключённый плагин `mypc windows` выполнил read-only проверку:

- Caddy — Compose-проект/service `caddy`, `/opt/remnawave/caddy/docker-compose.yml`, bridge `remnawave-network`, subnet `172.18.0.0/16`. Это не host network, поэтому `reverse_proxy 127.0.0.1:21800` из Caddy не работает с контейнером аккаунта.
- Caddyfile: `/opt/remnawave/caddy/Caddyfile` → `/etc/caddy/Caddyfile:ro`; webroot: `/opt/funtidesk-web/current` → `/usr/share/caddy:ro`; сертификаты в отдельном volume `caddy-ssl-data`.
- `current` указывает на каталог `/opt/funtidesk-web/releases/0344118bcc88a6185b81f701ba9e43d7e8705495-artifact`. Это статический каталог, не Git checkout. Public web manifest ранее совпал с закреплённым исходником.
- Account/SMTP/DKIM контейнеров пока нет; hbbs/hbbr используют `funtidesk-server:funtidesk-server-78e50da1aa01`. Этот старый образ не заявляется как поддерживающий новый resolver.
- Кандидаты `172.31.250.0/29` и `172.31.251.0/29` не пересекаются с проверенными Docker subnet/host routes. Перед изменением сети проверку повторяют.
- SSH `desk.funti.cc:22` с миниПК доступен с существующей аутентификацией. Из облачной среды был `Connection refused`; это не доказательство отказа SSH сервера.

2026-10-14 те же параметры Caddy/контейнеров подтверждены чтением через MCP `de_funti_cc` и SSH от DE. После повторной авторизации также проверены новые сети: `172.31.250.0/29`–`172.31.254.0/29` не пересекаются с прочитанными Docker subnets и host routes ни на Core, ни на DE. Проверку повторяют непосредственно перед запуском.

## Что предлагается

`compose.yaml` запускает account в трёх собственных внутренних сетях: frontend, SMTP и канал witness. Mail и переходник witness имеют разные выходные сети. Сам account не имеет выходной сети. Account не присоединяется к VPN/Postgres/Valkey-сети и не получает их volumes. Публичных портов у новых контейнеров нет. API работает от UID/GID `10001`, без capabilities, с ограничениями памяти/процессов; основной HMAC-ключ доступен только ему. Машинный ключ witness передаётся также независимому сервису, но не переходнику/Caddy.

`caddy-account.override.yaml` добавляет только Caddy к новой frontend-сети и сохраняет его прежнюю `remnawave-network`. Статический адрес Caddy `172.31.251.4` разрешён API как единственный доверенный proxy. `Caddyfile.desk.proposed` заменяет **только** существующий блок `desk.funti.cc`: API-prefix идёт в account без HTML-fallback; Caddy перезаписывает адрес клиента; `/account/` получает no-store и CSP; прежний сайт продолжает отдаваться тем же webroot. Остальные домены и SSL volume не изменяются.

`hbbs-identity.override.yaml` добавляет hbbs отдельный каталог Unix socket и переменные resolver. Account видит этот каталог read-only, без hbbs базы/приватного ключа. Нужен новый образ сервера из проверенного commit с resolver, а не текущий старый image. Контроль identity socket и ошибочного пути проверяется до включения маршрута.

Смена webroot symlink и добавление frontend-сети требуют согласованного recreate **только Caddy**, с исходным Compose и новым override; reload не меняет уже разрешённый bind mount. Перед этим сохраняют точные текущие конфиги и проверяют общий Caddyfile; нельзя заменять его целиком фрагментом desk. Откат возвращает прежние Caddyfile/Compose/webroot; уже поставленные удаления не откатываются.

## Независимое состояние на DE

`compose.witness.yaml` — отдельный Compose-проект на `de.funti.cc`: тот же проверенный account binary в режиме `witness`, UID/GID `10002`, свой каталог `/opt/funtidesk-account-witness`; основной account-ключ и база туда не монтируются. Caddy имеет отдельную входную сеть, а witness остаётся только во внутренней. У официального Caddy binary есть file capability; ему явно оставлен только `NET_BIND_SERVICE`. `NO_PROXY` исключает унаследованный proxy для внутреннего witness. Эти свойства проверены настоящим HTTPS-запросом, а не только адаптацией конфига. Caddy выдаёт только HTTPS `de.funti.cc:8447/v1/witness`, остальные пути — 404. Это отдельный сервис; действующий MCP на 8445 не используется для хранения данных кабинета.

TLS-конфигурация использует сертификат/ключ из отдельного закрытого каталога с `fullchain.pem` и `privkey.pem`. Файлы до применения проверяет оператор; автоматическое получение и продление здесь не настроены. Read-only проверка после переподключения обнаружила: **8446 занят действующим системным Caddy**, обслуживающим другой сайт с upstream `127.0.0.1:8220`. Его сертификат `de.funti.cc` доверен и действителен до 2026-12-03; это не сертификат нового сервиса. Поэтому проект перенесён на **8447**, свободный в момент проверки. Для собственного endpoint нужны согласованный способ получения/продления сертификата и проверка внешней доступности после запуска. На DE свободно 1 545 379 840 байт; дисковый запас и отсутствие пересечений сетей повторно проверяют до запуска. Существующие Caddy, MCP и приложения на DE не меняются этим проектом.

Core-переходник не имеет volumes/секретов: он передаёт только подписанное тело на закреплённый HTTPS-адрес, без cookies, редиректов и системного proxy. Инициализация обоих хранилищ выполняется явно и только один раз. Порядок и отказ при устаревшем состоянии — [ACCOUNT_RECOVERY.md](../../docs/ACCOUNT_RECOVERY.md), границы доверия — [ADR-011](../../docs/ADR-011-account-recovery.md).

## Артефакты и секреты

Образ сервера `funtidesk-account-server:ci` содержит hbbs/hbbr с opt-in resolver из того же commit, собственный source label и AGPL. `hbbs-registry` теперь не только проверяет модуль, но и собирает настоящие статические server binaries; CI не публикует серверный релиз. Это проверочная поставка; рабочее обновление hbbs/hbbr выполнено через `Server build` → `server-release.env` (`FUNTIDESK_SERVER_RELEASE`) и Compose с resolver override, с сохранением identity/data volumes. Для последующих операций использовать [действующую конфигурацию](../../docs/ACCOUNT_DEPLOYMENT.md#действующие-серверные-конфигурации). Новая проверка не заменяет согласованный серверный выпуск. Прежний production image без resolver для кабинета не подходит.

Account image содержит статический musl binary из успешного `Account checks` и текст AGPL из `client/LICENCE`, проверенные по SHA256SUMS и связанному commit/run. Dockerfile не включает исходники, mail credentials или hbbs данные; source URL и revision доступны в OCI labels. Build context создаётся вне репозитория из этого артефакта. Mail image фиксирует Debian digest; установленные версии Postfix/OpenDKIM и итоговый image digest сохраняют в manifest поставки. Пакетные лицензии Debian сохраняются внутри mail image.

Job `account-infra` того же workflow берёт binary из текущего run, проверяет его SHA-256, собирает три образа account/mail/server и запускает проверки ниже. Артефакт `funtidesk-account-infra-<commit>` содержит Docker archive трёх образов, source SHA, image IDs, manifests API/server binaries и версии пакетов и SHA256SUMS; ни ключей, ни писем в нём нет. Workflow имеет только `contents: read`, не публикует релиз и ничего не развёртывает. Images загружают только из выбранного успешного run, проверив manifest; пример `.env` заменяют конкретными проверенными image IDs/тегами.

Локально проверки повторяются с уже собранными образами:

```sh
python3 scripts/account/check-config.py
FUNTI_ACCOUNT_IMAGE=<проверенный-образ-API> \
FUNTI_ACCOUNT_MAIL_IMAGE=<проверенный-образ-SMTP> \
python3 scripts/account/smoke-mail.py
FUNTI_ACCOUNT_IMAGE=<проверенный-образ-API> \
FUNTI_ACCOUNT_MAIL_IMAGE=<проверенный-образ-SMTP> \
python3 scripts/account/smoke-witness-tls.py
```

Первая команда проверяет Compose и слияние Caddy override на минимальном fixture проверенных полей, затем валидирует предлагаемый desk-блок в закреплённом Caddy без сети. Это не проверка полного production Caddyfile. Вторая создаёт только временные контейнеры/тома/внутреннюю сеть, тестовые HMAC/DKIM keys, запрашивает код у настоящего API, читает подписанное письмо из изолированной очереди и открывает native session. Она запускает настоящий witness в отдельном тестовом томе, инициализирует основную базу явно и проверяет CLI restore: старый токен после восстановления недействителен. Она также проверяет отказ чужому sender и временный отказ после остановки DKIM, отсутствие секретов в stdout/stderr; SMTP наружу блокирован. Ресурсы удаляются в `finally`. Свободный test subnet по умолчанию `172.31.249.0/29` можно переопределить через `FUNTI_ACCOUNT_TEST_SUBNET`.

На сервере, только после разрешения:

- отдельный `/opt/funtidesk-account` с защищёнными каталогами data/secrets/mail-queue/identity;
- HMAC: случайные 32 байта в hex, владелец файла UID `10001`, права `0400`; папка data UID/GID `10001`, `0700`;
- identity directory: root, группа `10001`, проход для этой группы; socket `0660`;
- DKIM RSA 2048+ создаётся **на сервере**, selector `funtidesk202610`, домен `funti.cc`; private key `0600`, не выводится и не попадает в Git. Публичный TXT передаётся владельцу отдельно;
- `.env` с проверенными image/адресами, без секретных значений; секреты доступны только назначенному контейнеру. Пример `.env.example` не является production env.

Mailer принимает SMTP только на своей private-границе `172.31.250.2:2525` от account subnet, не слушает публичный 25 и не требует стороннего почтового API. Envelope sender — `no-reply@funti.cc`; SMTP hostname и HELO — `desk.funti.cc` (решение владельца 2026-10-15). DKIM обязателен, сбой milter отклоняет отправку временно. SMTP наружу требует проверенный TLS; очередь живёт не более 5 минут. Postfix/OpenDKIM не пишут адреса/коды в stdout/syslog; операторские проверки показывают только агрегированные количества. Доставку Gmail/Яндекса/Mail.ru это пока не доказывает.

## DNS для владельца

Read-only DNS-проверка 2026-10-13: `desk.funti.cc` и `core.funti.cc` разрешаются в `173.249.195.36`. У `funti.cc` **уже есть** SPF:

```text
v=spf1 mx a:funti.cc ip4:172.245.108.154 include:sendinblue.com ~all
```

Нужна замена этой единственной SPF TXT, сохраняющая существующих отправителей и добавляющая фактический IPv4 нашего SMTP. При подтверждённом исходящем `173.249.195.36` предлагаемое значение:

```text
v=spf1 mx a:funti.cc ip4:172.245.108.154 ip4:173.249.195.36 include:sendinblue.com ~all
```

Не создают вторую SPF запись и не удаляют существующих отправителей. MX не меняется: наш контейнер только отправляет. Подтверждённый исходящий IPv4 — `173.249.195.36`; PTR должен возвращать `desk.funti.cc`, а A этого имени — тот же IP. PTR меняется у VPS-провайдера, не в Cloudflare. Системный hostname Core менять не требуется.

DKIM: TXT `funtidesk202610._domainkey.funti.cc` со значением `v=DKIM1; k=rsa; p=<публичный ключ, созданный на сервере>`. Это место для **публичного** значения; dummy/test key в production DNS не используется.

DMARC уже установлен: `_dmarc.funti.cc`, `v=DMARC1; p=none`. Для тестовой приёмки его не нужно дублировать или менять. Повышение политики и адрес отчётов — отдельное решение после проверки всех существующих отправителей.

## Backup/restore и критерии запуска

Нельзя просто добавить account в прежний tar `data/`: SQLite snapshot должен быть согласован с WAL, HMAC/DKIM keys защищены, резервные копии зашифрованы для владельца. Старый снимок сессий/nonce/challenge не запускают: их инвалидируют до старта. Локальные family ledgers на компьютерах не заменяются серверным backup.

Кроме снимка нужен **независимый актуальный журнал отзывов и подтверждённая последняя отметка**. Восстановление старого account DB без последних отзывов оставляет выключенный потерянный компьютер доверенным на ещё не получивших событие источниках. В прототипе ADR-011 есть независимая зашифрованная SQLite-копия, цепочка отметок и проверка свежести до старта; локальные тесты проходят, но это ещё не утверждённая схема и не проверенное восстановление на отдельном рабочем сервере. Имеющиеся prepare/stage/activate helpers сами по себе **не объявляют сервис принятым в production**. Restore выполняется только явно в новый путь по регламенту; успешный запуск контейнера не меняет этот статус.

До включения: архитектурное ревью ADR-010/011; точный итоговый Windows build и storage checks; независимый журнал и восстановление, сроки хранения/удаление аккаунта; Caddy validation/headers/CSRF/private network; свой SMTP с SPF/DKIM/DMARC; реальная доставка во входящие; два Windows-клиента и браузер, restart/offline/replay и сетевой захват. Образ клиента и backend/website фиксируют по точным SHA. Merge, production и выпуск — последним шагом после согласия владельца.
